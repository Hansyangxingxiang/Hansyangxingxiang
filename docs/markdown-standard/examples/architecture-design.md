> 示例说明：本文用于演示设计文档结构与 ASCII 图示写法。`ExampleBlockStore`、`ExampleScheduler`、`ExampleStore` 及全部数字均为虚构，不对应任何真实产品或现网结论。

## 1. 背景与目标

块存储客户端需要把卷的线性地址映射到一个或多个副本，并在副本故障时保持可读。当前合成系统存在三个问题：

1. 卷到副本的映射只保存在客户端内存，进程重启后需要全量重扫。
2. 控制路径与数据路径共用一条 TCP 连接，元数据更新会阻塞 IO。
3. 副本切换没有明确的完成条件，调用方无法判断何时可以安全重试。

目标：

- 卷映射持久化到元数据服务，客户端重启后按需加载。
- 控制路径与数据路径分离；元数据更新不进入 IO 关键路径。
- 副本切换定义单一提交点，提交前的失败可重试，提交后的失败按新映射处理。

非目标：不改变数据副本布局，不引入新的纠删码模式，不覆盖跨集群迁移。

## 2. 需求分析

| 需求 | 优先级 | 验收条件 |
|---|---|---|
| 卷映射持久化 | P0 | 客户端重启后不依赖全量重扫即可打开卷 |
| 控制与数据路径分离 | P0 | 元数据更新期间已有 IO 不增加排队 |
| 副本切换可判定 | P0 | 切换前后各有一个明确状态，调用方按状态决定重试 |
| 兼容旧客户端 | P1 | 旧客户端仍可按原协议打开卷 |

约束：元数据服务按单卷串行处理变更；客户端不持久化任何副本数据；切换期间允许短暂双读，不允许双写。

## 3. 总体设计

**图 1：ExampleBlockStore 部署与路径划分**

```text
                       control path (gRPC)
  +-------------+  --------------------------->  +------------------+
  | Example     |                                 | Example          |
  | Scheduler   |  <---------------------------  | Metadata Service |
  +------+------+        volume state             +------------------+
         |
         | data path (RDMA / TCP)
         v
  +------+------+        +-------------+         +------------------+
  | Example     | -----> | Example     |  ---->  | Example          |
  | Client      |        | Volume      |         | Store (replica)  |
  +-------------+        +-------------+         +------------------+
```

控制路径负责卷创建、映射查询与副本切换；数据路径只承载读写请求。客户端从元数据服务取得映射后缓存，映射带版本号；版本变化时客户端在下一次 IO 前刷新，而不是在 IO 中同步查询。

组件职责：

| 组件 | 职责 | 不负责 |
|---|---|---|
| ExampleScheduler | 选择副本、发起切换、等待提交 | 承载用户 IO |
| Metadata Service | 保存卷映射与版本、串行化变更 | 数据读写 |
| ExampleClient | 缓存映射、发送 IO、处理重定向 | 决定副本布局 |
| ExampleStore | 接收副本 IO、返回完成状态 | 维护卷级映射 |

被否方案：让客户端在 IO 超时时直接查询元数据服务。该方案把控制路径重新引入数据路径，且超时放大时会造成元数据服务过载，因此不采用。

## 4. 详细设计

卷映射结构：

| 字段 | 类型 | 语义 |
|---|---|---|
| `volume_id` | uint64 | 卷标识，创建后不变 |
| `map_version` | uint64 | 每次映射变更递增 |
| `primary` | endpoint | 当前主副本地址 |
| `secondaries` | endpoint[] | 只读副本地址 |
| `state` | enum | `ACTIVE` / `SWITCHING` / `DEGRADED` |

打开卷的流程：

1. 客户端以 `volume_id` 调用 `LookupMap`，携带本地缓存的 `map_version`。
2. 元数据服务版本相同则返回 `NOT_MODIFIED`，否则返回完整映射与新版本。
3. 客户端校验主副本可达后进入 `ACTIVE`；主副本不可达时进入 `DEGRADED` 并只读。

切换流程：

1. 调度器调用 `BeginSwitch(volume_id)`，元数据服务把状态置为 `SWITCHING` 并递增版本。
2. 调度器等待旧主副本排空在途写，然后调用 `CommitSwitch` 指定新主副本。
3. 元数据服务提交后状态回到 `ACTIVE`；客户端下次 IO 前刷新映射。

接口只交换映射与状态，不传递用户数据。`BeginSwitch` 可重复调用但只有第一次生效；`CommitSwitch` 必须携带 `map_version`，版本不匹配时拒绝，避免旧调度器覆盖新状态。

## 5. 数据一致性与并发设计

并发检查覆盖以下窗口：

| 场景 | 风险 | 处理 |
|---|---|---|
| 切换与客户端写并发 | 旧主副本已排空但客户端仍持有旧映射 | 提交前拒绝旧版本写，客户端重定向 |
| 双调度器并发切换 | 后提交者覆盖先提交者 | `CommitSwitch` 版本校验 |
| 客户端刷新与本地缓存 | 读到半更新的主副本与副本列表 | 映射整体替换，不逐字段更新 |
| 元数据服务重启 | 状态停留在 `SWITCHING` | 启动时按持久化版本恢复，未提交则回到 `ACTIVE` |

单一提交点是 `CommitSwitch` 的成功返回。提交前失败：映射未变，调用方可重试；提交后失败：映射已变，调用方必须按新版本处理，不能按旧主副本重试。

不变量：同一卷在任一时刻最多一个 `primary`；`map_version` 单调递增；`SWITCHING` 状态下不允许新的写请求进入旧主副本。

## 6. 兼容性与升级

- 旧客户端不发送 `map_version`，元数据服务按版本 0 处理并返回完整映射；旧客户端忽略新字段。
- 新客户端连接旧元数据服务时，`BeginSwitch` 返回 `UNIMPLEMENTED`，客户端保持原映射，不进入 `SWITCHING`。
- 升级顺序：先元数据服务，再调度器，最后客户端。回滚只回滚客户端时，`SWITCHING` 状态仍可被新调度器提交。
- 回滚限制：一旦提交了新主副本，旧客户端缓存需要刷新；不支持仅靠进程回滚恢复旧映射。

## 7. 监控、测试与验收

| 指标 | 单位 | 观测点 | 告警阈值（示例） |
|---|---|---|---|
| `map_refresh_total` | 次 | 客户端 | 无 |
| `switch_duration_seconds` | 秒 | 调度器 | 大于 30 秒 |
| `io_rejected_stale_map` | 次 | 客户端 | 持续大于 0 |
| `switching_volumes` | 个 | 元数据服务 | 大于 5 |

测试矩阵：

| 测试 | 方法 | 期望 |
|---|---|---|
| 客户端重启 | 打开卷后重启进程 | 不触发全量重扫，按版本加载 |
| 切换中断 | 在 `BeginSwitch` 后停止调度器 | 状态可恢复，写不被误导 |
| 双调度器 | 并发提交不同版本 | 仅一个提交成功 |
| 旧客户端 | 使用版本 0 协议打开卷 | 可读写，字段被忽略 |

验收标准：上述四项全部执行并通过；性能项“元数据更新不增加已有 IO 排队”需在真实环境测量，本示例未执行，标记为未验证。

## 8. 风险与遗留问题

1. 元数据服务单卷串行化在切换频繁时可能成为瓶颈；当前不做分片，待真实负载验证。
2. `SWITCHING` 状态依赖调度器存活；调度器崩溃后的超时回收策略未定。
3. 客户端只读降级期间不保证读延迟，未给出 SLA。
4. 本文所有组件、接口与数字均为示例，不能作为实现或验收依据。
