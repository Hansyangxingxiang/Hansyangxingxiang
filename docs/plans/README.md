# 计划与执行台账

本目录保存复杂研发任务的项目内计划与执行记录。它服务于 `plan-driven-development` 工作流，不是 Claude Code 原生 Plan Mode 的计划目录。

## 与原生 Plan Mode 的关系

- 原生 Plan Mode 负责批准前的权限限制与交互式计划确认；其计划文件由客户端管理，通常在 `~/.claude/plans/`，不手工编辑。
- 本目录中的文件是**项目执行台账**：记录确认后的步骤、状态、偏差、验证与报告，可提交、可跨会话恢复。
- 计划确认不等于执行授权。批准后，仍需用户明确要求开始执行，才创建或更新本目录文件并修改项目。
- Plan Mode 内不写本目录；退出并取得执行授权后再落盘。

## 命名

```text
docs/plans/YYYY-MM-DD-task-name.md
```

- 日期用创建计划的实际日期，不根据文件时间推断。
- `task-name` 用小写 kebab-case，写任务而非文档类型，例如 `2026-11-20-skill-rule-consolidation.md`。
- 同一任务多阶段扩展时沿用原文件，不按阶段拆成多份台账。
- 示例放在 `examples/`，不参与真实任务命名。

## 状态

| 状态 | 含义 | 进入条件 |
|---|---|---|
| `草稿` | 计划撰写中 | 正在分析或起草 |
| `待确认` | 计划已完整，等待用户确认 | 自检完成 |
| `已确认待执行` | 方案已接受，尚未授权修改 | 用户确认计划 |
| `执行中` | 已授权并开始修改 | 用户明确要求执行 |
| `已验证` | 验收项有证据结论 | 验证完成 |
| `已完成` | 验证、报告与台账均完成 | 最终报告交付 |
| `已阻塞` | 等待依赖、环境或决策 | 阻塞原因已记录 |
| `已取消` | 不再执行 | 用户取消或方案废弃 |

状态只写在计划文件。对话中的“可以”“看起来不错”不等于执行授权；语义模糊时只确认一次。

## 创建

1. 复制 `templates/plan-driven-development.md`。
2. 填背景、目标、非目标、现状、方案、影响文件、实施步骤、验证、风险、回滚。
3. 每步写完成条件与验证方式；不写“优化相关代码”类空步骤。
4. 计划确认后状态置 `已确认待执行`；获得执行授权后置 `执行中`。

## 中断恢复

1. 读计划文件的元数据、实施清单与执行记录。
2. 检查 `git status`、`git diff` 与相关提交。
3. 核对已有测试输出与验证记录。
4. 从首个未完成步骤继续；已完成项不重做。
5. 无法确认的完成项重跑验证，不凭记忆标记完成。
6. 计划文件缺失时说明证据边界并重新规划，不假装延续。

恢复不是重新审批：范围与设计未变时继续；出现重大设计变化、数据迁移或破坏性操作时停止并重新评审。

## 完成

- 检查实际 diff，运行适用的构建、测试与静态检查。
- 验收项逐条判定；未运行或受阻项单列。
- 更新状态到 `已验证`，再写最终报告后置 `已完成`。
- 失败、未运行项和剩余风险不得省略；不能声称全部通过。
- 计划文件随任务提交；是否提交由用户决定，不自动 push。

## 格式检查

```bash
python3 skills/writing/markdown-document-standard/scripts/doc_lint.py --doctype plan docs/plans/2026-11-20-task-name.md
```

用 `--profile new` 检查新台账，旧台账用 `--profile legacy`。静态检查不能验证技术结论、测试真实性或验收判定。
