# Workflow: storage-bug-analysis

## 目的

从故障现象出发，通过分层定位与源码分析反推根因，形成证据链，产出修复方案与测试方案，并归档。

## 适用场景

- 空间未释放
- 性能异常
- IO 行为不符预期
- 崩溃 / 卡死
- 数据不一致

## 阶段流水线

```
故障现象
  → storage-debug（分层定位 / 假设验证）
  → 源码分析
  → 调用链
  → 根因
  → 修复方案
  → design-document
  → 测试方案
```

## 每阶段用到的 Skill

| 阶段 | Skill |
|---|---|
| 故障现象 → 根因 | `storage-debug` |
| 源码分析 / 调用链 | `storage-code-analysis` |
| 修复方案 / 测试方案 | `design-document` |

## 产出物

- 根因分析（含证据链）
- 修复方案设计
- 测试方案
- 分析归档（按目标项目规范，参考 `templates/bug-analysis.md`）

## 检查清单

- [ ] 从现象反推，不先入为主
- [ ] 假设表：每个假设有验证实验，不靠猜
- [ ] 根因状态明确；未确认时列出候选解释、反证及下一步实验；已确认根因有证据链（`file:line` 实读 + 日志 + git 定年）
- [ ] 区分"当前实现"与"目标实现"
- [ ] 修复方案覆盖异常路径与并发
- [ ] 测试方案可复现、可判定
- [ ] 归档含 8 槽（概要 / 后果 / 触发链 / 触发条件 / 来源定年 / 发现过程 / 修法建议 / 处置状态）

## 阶段交接与完成状态

交接时携带输入范围、项目与版本、产物路径或正文、证据引用、验证状态及待确认项。同一版本且相关文件与条件未变化时复用已核验记录，变化时仅重核受影响部分。后续阶段不得默认上游推断已成为事实。

按用户范围执行必要阶段；已有产物满足条件时直接从对应阶段继续。明确区分分析完成、设计完成、执行验证与归档完成；未执行的实验和未完成的客户端预览单独列出。
