# Workflow: storage-feature-design

## 目的

把一个存储功能需求，从需求出发，经过现状 / 源码 / 约束分析，产出一份完整、可评审、可实现、可测试的设计文档，并按项目规范归档。

## 适用场景

- 新模块设计
- 功能改造
- 技术选型
- 架构评估

## 阶段流水线

```
需求
  → 现状分析
  → 源码分析
  → 约束分析
  → 方案设计
  → 并发/一致性分析
  → 异常处理
  → 兼容/升级
  → 测试设计
  → 设计文档
  → 按项目规范归档（NeonSAN 项目按需使用 neonsan-docs，personal-notes 仓库维护）
```

## 每阶段用到的 Skill

| 阶段 | Skill |
|---|---|
| 现状分析 / 源码分析 | `storage-code-analysis` |
| 方案设计 / 并发一致性 / 异常 / 兼容升级 / 测试设计 | `design-document` |
| 项目归档 | 确认是 NeonSAN 时使用 `neonsan-docs`（personal-notes 仓库维护）；其他项目遵循自身规则 |

## 产出物

- 设计文档（按规模选择轻量或完整模式，见 `templates/design-document.md`）
- 归档后的设计文档（目标项目规范落盘）

## 检查清单

- [ ] 现状与问题先讲清楚，再谈需求，最后才进入设计
- [ ] 每条结论带出处（`file:line` 实读，不凭记忆）
- [ ] 有非目标（明确不做 + 原因）
- [ ] 方案有对比（被否方案 + 原因 + 最终选择理由）
- [ ] 并发场景覆盖 Write / Discard / Snapshot / Clone / COW / Recovery
- [ ] 异常路径覆盖成功 / 失败 / 超时 / 重试 / 重复 / 节点故障 / 重启 / 升级 / 回滚
- [ ] 兼容性覆盖 Old↔New 版本 / 数据 / 配置 / 升级 / 回滚
- [ ] 验收标准可执行、可判定
- [ ] 风险栏不虚构，明确标注"明确不修"项
- [ ] 归档符合实际项目规范（命名 / 落盘 / 术语）

## 阶段交接与完成状态

交接时携带输入范围、项目与版本、产物路径或正文、证据引用、验证状态及待确认项。同一版本且相关文件与条件未变化时复用已核验记录，变化时仅重核受影响部分。后续阶段不得默认上游推断已成为事实。

按用户范围执行必要阶段；已有产物满足条件时直接从对应阶段继续。明确区分分析完成、设计完成、执行验证与归档完成；未执行的实验和未完成的客户端预览单独列出。
