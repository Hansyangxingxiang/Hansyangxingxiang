# Workflow: technical-writing

## 目的

按用户目标规划、撰写或调整技术内容；语言润色和微信 HTML 排版按需进入。普通博客和原理系列不默认生成公众号版本。

## 入口路由

| 用户任务 | 主导 Skill | 完成条件 |
|---|---|---|
| 解释项目机制、规划原理系列、评审技术证据、检查系列一致性 | `writing-project-principles` | 对应任务的计划、正文、评审或冲突清单 |
| 公众号选题、标题与面向读者的表达；已有文章调整公众号版本 | `wechat-tech-article` | 内容稿或指定范围的表达修订 |
| 已有文本只需语言润色 | `humanizer-zh` | 保持事实、技术限定与作者声音的修订稿 |
| 已有 Markdown 只需微信 HTML | `producing-tech-blog` | 内容保真的 HTML 与检查状态 |

“写公众号原理文章”由 writing-project-principles 负责机制与证据，wechat-tech-article 按需处理标题与读者表达，不重复建立证据基线。用户只要求系列规划或评审时，不继续生成正文。

## 阶段流水线

```
任务与现有资料
  → 选择对应入口（复用已有证据与产物）
  → 按需调整公众号表达
  → 按需使用 humanizer-zh 润色并核对信息保真
  → 仅在用户要求微信 HTML 时使用 producing-tech-blog
```

## 产出物

交付与请求对应的系列计划、作者记录、文章、评审报告或一致性冲突清单。仅在实际经过相关阶段时交付润色稿和 HTML，不为凑齐工作流生成无关文件。原理文章参考 writing-project-principles 的 assets；公众号表达可参考 `templates/technical-article.md`，均按内容选择结构。

## 检查清单

- [ ] 开头适合读者与文章目的，结构按内容选择
- [ ] 事实 / 分析 / 观点三分离
- [ ] 英文技术词保留原文
- [ ] 润色未新增事实、作者经历或反馈，未改变数字、技术语义和不确定性
- [ ] 若要求微信 HTML，检查内联 CSS、内容完整性，并单独记录客户端预览状态
- [ ] 若为系列，术语、版本与结论一致；篇目结构按主题调整

## 阶段交接与完成状态

交接时携带输入范围、项目与版本、产物路径或正文、证据引用、验证状态及待确认项。同一版本且相关文件与条件未变化时复用已核验记录，变化时仅重核受影响部分。后续阶段不得默认上游推断已成为事实。

按用户范围执行必要阶段；已有产物满足条件时直接从对应阶段继续。明确区分分析完成、设计完成、执行验证与归档完成；未执行的实验和未完成的客户端预览单独列出。
