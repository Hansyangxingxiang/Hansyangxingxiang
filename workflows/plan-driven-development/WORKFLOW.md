# Workflow: plan-driven-development

## 目的

为复杂研发任务提供通用执行治理：先把需求、现状、方案、影响面、步骤、风险、验证与回滚写成可执行计划；评审并由用户确认后再执行；执行中按步骤推进并留台账；完成后用实际证据验收并向用户报告。领域内容仍由对应 Workflow 与 Skill 决定。

## 适用场景

- 跨文件、跨模块、跨技能的改造或整合。
- 需要设计取舍、兼容/数据/并发风险分析的多步骤任务。
- 需要用户先确认方案，或执行可能跨会话、需要恢复。
- 在领域 Workflow 之外，需要统一的“计划确认、执行授权、验证报告”纪律。

不适用：单文件低风险小修；纯研究、排障、方案内容或写作任务；用户已选择 Superpowers 计划技能。

## 阶段流水线

```text
Plan
  需求与边界 → 读代码/文档 → 影响面与依赖 → 方案对比 → 步骤/验收/风险/回滚
    ↓（计划草稿，Plan Mode 内不写项目文件）
Review
  需求 / 设计 / 影响 / 兼容 / 并发 / 测试 / 回滚门槛 → 用户确认
    ↓（计划确认；不等于执行授权）
Execute
  显式执行授权 → 落盘 docs/plans/YYYY-MM-DD-task-name.md → 分步实施 → 更新台账
    ↓
Verify
  实际 diff → 构建/测试/静态检查 → 兼容与异常路径 → 验收逐条判定
    ↓
Report
  变更文件 / 决策 / 验证结果 / 未运行项 / 风险 / 后续 → 更新计划状态
```

**图 1：计划驱动研发的五个阶段与授权门槛。** 箭头表示阶段推进；领域 Workflow 可作为 Plan 输入或 Execute 的领域阶段，不改变本流程的确认与验证门槛。

领域 Workflow 可作为 Plan 输入，也可是 Execute 的领域阶段：例如存储功能设计先由 storage-feature-design 完成设计文档，再由本工作流治理实施；本工作流不重做领域分析。

## 每阶段用到的 Skill

| 阶段 | Skill | 职责边界 |
|---|---|---|
| Plan | `plan-driven-development` | 复杂任务判定、计划质量契约、影响面与回滚要求 |
| Plan（领域输入） | `design-document` / `storage-code-analysis` / `storage-debug` | 按任务提供方案、源码事实或根因；本工作流不替代 |
| Review | `plan-driven-development` | 七项门槛与用户确认；领域技能只回答技术问题 |
| Execute | `plan-driven-development` + 领域 Skill | 本技能管范围、步骤、台账与停止条件；领域 Skill 管具体修改方法 |
| Verify | `plan-driven-development` + 可用的构建/测试/静态工具 | 证据记录与验收判定；不把未运行写成通过 |
| Report | `plan-driven-development` | 汇总变更、决策、验证、受限项与后续 |
| 格式检查 | `markdown-document-standard` | 计划文件与交付文档格式；不验证技术结论 |

## 产出物

- 计划草稿：Plan Mode 中的计划内容（不写项目文件）。
- 执行台账：`docs/plans/YYYY-MM-DD-task-name.md`，结构见 `templates/plan-driven-development.md`。
- 实际变更：计划内文件与必要生成物。
- 验证记录：命令、输出摘要、通过/失败/未运行/受阻。
- 最终报告：完成项、变更文件、关键决策、验证结果、剩余问题、风险与下一步。

不要求每个任务都产生全部文档；只按复杂度交付，避免为凑流程创建空文件。

## 检查清单

- [ ] 计划包含背景、目标、非目标、现状、方案、影响文件、实施步骤、风险、验证、回滚
- [ ] 每个步骤有可验证的完成条件，无“优化相关代码”类空步骤
- [ ] 影响面覆盖调用方、数据、配置、兼容、生成物与跨仓库边界
- [ ] 用户已确认方案；执行前已获得显式执行授权
- [ ] 执行前检查 Git 状态，未覆盖用户未提交修改
- [ ] 只改计划内路径；偏差、发现与新风险已记录
- [ ] 实际 diff 已检查；测试/检查结果按实记录，未运行项单列
- [ ] 计划状态与台账、验收结论一致

## 横向约束（全部阶段）

- 交付物格式、元数据与静态检查遵循 `markdown-document-standard`；计划文件用 `--doctype plan`。
- 技术图默认 ASCII；仅用户明确要求或平台明确需要时用 Mermaid。
- 事实 / 推断 / 建议 / 待验证分离；`file:line` 必须本轮实读。
- 不写 `~/.claude/plans/`，不模拟原生审批；项目台账只写 `docs/plans/`。
- 复杂任务进入执行前遵守本工作流的计划确认与执行授权；领域 Workflow 只写指针，不复制审批规则。

## 阶段交接与完成状态

交接时携带：任务边界、计划路径、当前状态、已完成/未完成步骤、Git 与验证状态、待确认项。后续阶段不得把“计划已批准”当成“文件已修改”，也不得把“执行完成”当成“已验证”。

明确区分：

- **计划确认**：方案可接受，状态可到 `已确认待执行`。
- **执行授权**：用户明确要求开始修改。
- **执行完成**：步骤已做，可能有未验证项。
- **已验证**：验收项有证据结论。
- **已完成**：验证、报告、台账更新均完成；受限项已单列。

中断后从首个未完成步骤恢复；无法确认的完成项重跑验证。计划取消或阻塞时保留原因与影响，不删除历史记录。
