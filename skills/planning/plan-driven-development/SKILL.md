# Plan-Driven Development — 复杂研发任务的计划与执行治理

## Overview

本技能解决“复杂任务如何从计划走到可验证结果”：在写文件前形成可执行计划，先评审再执行，执行中保持范围与台账，完成后用实际证据验收。它治理的是**过程**，不决定“做什么技术方案”。

五阶段：**Plan → Review → Execute → Verify → Report**。计划文件是跨会话执行台账；原生 Plan Mode 是权限与计划确认交互，两者不互相替代。

## When to Use / NOT

适用：

- 任务跨多个文件、模块、技能或阶段，无法一次改完并直接判断正确性。
- 存在设计取舍、数据/兼容/并发风险，或需要回滚方案。
- 需要用户先确认方案，或执行可能跨会话、需要恢复。
- 需要明确“改了什么、验证了什么、还有什么没验证”。

不适用：

- 单文件、低风险、结果可直接判断的小修 → 直接做。
- 纯技术研究、源码分析、排障、方案内容、文章写作 → `storage-code-analysis`、`storage-debug`、`design-document`、`writing-project-principles` 等。
- 用户已明确选择 superpowers 的 writing-plans / executing-plans → 让位，不叠加第二套台账。
- 只需要领域流水线 → 对应 Workflow；本技能只提供执行治理。

## Plan Mode 与授权边界

- 原生 Plan Mode 在批准前限制文件修改，权限由客户端执行；本技能不绕过、不模拟。
- 原生计划文件由客户端管理（通常在 `~/.claude/plans/`），**不是项目产物**；不手工编辑，不假设可写。
- 在 Plan Mode 中：只调研、分析并输出计划；不创建 `docs/plans/` 文件，不修改项目文件，等待原生计划确认。
- **计划批准不等于执行授权**。批准只表示方案可接受；进入写文件前还需用户明确表达“开始执行/按计划修改”。若批准消息已明确包含执行意图，可直接继续；语义模糊时只问一次。
- 退出 Plan Mode 后的第一次写入前，先确认：计划已确认、执行已授权、Git 状态允许、目标文件无用户未提交改动冲突。

## 计划质量契约

计划至少回答：

- **背景与现状**：为什么做；当前实现、约束与已确认事实。
- **目标与非目标**：可验证结果；明确不做什么及原因。
- **方案与决策**：选择理由、被否方案、影响面；不把未验证推断写成事实。
- **影响文件**：新增/修改/删除；接口、数据、配置、生成物、兼容性。
- **实施步骤**：每步可执行、有完成条件与验证方式；不写“优化相关代码”“处理边界情况”。
- **风险与回滚**：触发信号、缓解措施、回滚单位与回滚后验证。
- **验证与验收**：命令、期望结果、未运行项如何标注。

计划文件结构以 `templates/plan-driven-development.md` 为准，本技能不复述章节清单。

## Review 门槛

执行前逐项检查：

- 需求是否被正确理解，目标是否可判定。
- 设计是否合理，是否覆盖被否方案与关键取舍。
- 影响面是否完整：调用方、数据、配置、兼容、生成物。
- 数据与元数据是否兼容升级/降级/回滚。
- 并发、一致性、异常路径是否分析；不适用时说明原因。
- 测试是否足以证明验收，是否包含失败与边界路径。
- 回滚是否可执行，是否有不可逆操作。
- 是否触碰用户未提交改动、受保护文件或跨仓库边界。

任一项不成立：回到规划；不带着已知缺口进入执行。复杂任务需用户显式确认。

## Execute 纪律

- 先建立或更新 `docs/plans/YYYY-MM-DD-task-name.md`，状态置 `执行中`；再改代码。
- 一次只做一个可验证步骤；完成后立即更新清单、执行记录与验证结果。
- 只修改计划内路径；不顺手重构、不扩大需求。
- 不覆盖用户已有未提交修改；发现冲突先停止并说明。
- 重大设计变化、数据迁移、破坏性操作：停止执行，重新评审并取得授权。
- 新发现写入“执行记录/偏差”，不悄悄改变计划。

## Verify 证据

- 检查实际 diff 与计划是否一致，列出未计划改动。
- 运行适用的构建、测试、静态检查、兼容与异常路径验证。
- 按验收标准逐条判定；不能运行的测试标 `未运行` 或 `受阻` 并说明原因。
- 失败必须分析原因并记录；不忽略、不把“未运行”写成“通过”。
- 静态检查通过不等于运行时、客户端或技术结论通过。

## 状态与恢复

状态词表：`草稿` → `待确认` → `已确认待执行` → `执行中` → `已验证` → `已完成`；异常 `已阻塞`、`已取消`。

跨会话恢复顺序：

1. 读计划文件状态、清单与执行记录。
2. 查 `git status` / `git diff` / 相关提交。
3. 核对已有测试与验证输出。
4. 从首个未完成步骤继续；已完成项不重做。
5. 无法确认的完成项重跑验证，不凭记忆标记完成。

计划文件缺失：先说明无法恢复的证据边界，再重新规划；不假装延续旧计划。

## 与既有 Workflow / Superpowers 的关系

- 领域 Workflow（storage-feature-design、storage-bug-analysis、storage-performance-analysis、technical-writing）决定技术阶段与内容技能；本技能只治理复杂任务的计划、授权、执行与验收。
- 同一审批规则只在 `SKILL.md` 定义；领域 Workflow 只写一行指针。
- Superpowers 的 writing-plans / executing-plans 是另一套实现方法论（任务粒度、TDD、worktree、subagent 评审）。用户选择其中之一时让位；不混用台账。

## 输入、交付与完成条件

- 输入：任务目标、范围、已有产物、项目规则、Git 状态。
- 交付：已确认的计划、执行台账、实际变更、验证结果与最终报告。
- 完成条件：验收项逐条有结论；未运行/受阻项单列；计划状态与实际一致。
- 通用证据分级、输入不足与交付复用遵循 `references/shared-method.md`。
