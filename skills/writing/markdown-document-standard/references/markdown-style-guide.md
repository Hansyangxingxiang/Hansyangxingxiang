# Markdown 基础排版规范

本文件是技术文档正文格式的唯一权威源。领域技能不复述这些规则；需要时按技能名引用 `markdown-document-standard`。

## 一、标题

### 1.1 一级标题

每篇文档只使用一个 H1，放在文件开头：

```markdown
# 文档标题
```

不使用多个 H1 分篇；不把 H1 当作章节标题。

### 1.2 章节编号

技术文档的主要章节建议编号，层级与编号一致：

```markdown
## 1. 背景与目标

### 1.1 项目背景

### 1.2 设计目标

## 2. 总体架构
```

要求：

- 编号连续，不跳号；同级标题使用同一种编号风格。
- 标题层级不跳跃（H2 下直接出现 H4 视为错误）。
- 原则上不超过四级标题（H4）；需要更深层级时改为列表或拆文档。
- 不使用装饰性符号、Emoji 或“第 X 部分”与数字编号混用。
- 已有文档若已形成稳定编号体系，优先保留，不因套模板重排。
- 附录、参考、实现参考、术语表、修订记录、检查清单可以不编号。

### 1.3 标题写法

标题简洁准确，能单独说明该节回答什么问题。避免“其他”“相关内容”“补充说明”这类无信息标题；不为凑章节增加标题。

## 二、段落

- 一个段落表达一个主要观点；复杂机制分步骤解释。
- 重要结论先给出，再解释依据与边界。
- 不把全文写成多层列表；也不把每句话单独成段。
- 避免连续大段文字；技术说明可按以下顺序展开：

1. 解决什么问题。
2. 为什么需要这种设计。
3. 系统如何实现。
4. 正常情况下如何工作。
5. 异常情况下如何处理。
6. 有哪些限制与取舍。

## 三、空行与缩进

- 标题前后各保留一个空行。
- 段落之间保留一个空行。
- 表格前后各保留一个空行。
- 代码块前后各保留一个空行。
- 列表嵌套统一使用两个空格或四个空格，同一文档保持一致。
- 不使用连续多个空行制造间距；不使用行尾空格强制换行（确需硬换行时使用 `<br>` 或在 diff 中说明）。
- 文件末尾保留一个换行，不留多余空行。

## 四、加粗与强调

适度加粗：

- 关键技术结论。
- 核心设计约束。
- 重要风险与边界条件。
- 首次定义的关键术语。

避免：

- 整段加粗或每句都加粗。
- 用 Emoji 代替技术说明。
- 用斜体表达强调之外的含义。
- 在标题中加粗或添加装饰。

## 五、列表

- 有明确先后顺序的流程、步骤、检查项使用有序列表。
- 无先后关系的分类、组件、条件使用无序列表。
- 复杂机制优先“图 + 分步骤说明”，不要用多层嵌套列表替代流程。
- 列表项保持同一语法层级；必要时用一句话说明列表的适用范围。
- Checklist 使用 `- [ ]` / `- [x]`，只用于可验证的完成条件。

## 六、表格

适合表格：

- 参数与字段说明。
- 模块/组件职责。
- 方案比较与取舍。
- 接口与状态转换。
- 错误处理与版本兼容。
- 测试矩阵与风险评估。

要求：

- 表头简洁，列数尽量不超过 5 列；过宽时拆表或改为正文。
- 分隔行合法（`| --- | --- |`），每行列数与表头一致。
- 单元格内不写多段论述；复杂问题用正文解释。
- 技术结论必须与正文一致；表中数字带单位与条件。
- 单元格内的竖线写作 `\|`；代码中的 `|` 放入反引号并转义。

## 七、代码块

所有围栏必须闭合，并标注语言：

- `bash`：命令与脚本调用。
- `c` / `cpp` / `go` / `python`：源码。
- `json` / `yaml`：配置与数据。
- `text`：ASCII 图、日志、协议报文、无法高亮的伪代码。

要求：

- 命令、日志、源码、ASCII 图必须明确区分；ASCII 图一律用 `text`。
- 代码示例尽量可运行；伪代码必须标注“伪代码”。
- 日志不得改写；截断时标注省略位置。
- 路径、参数、错误码、函数名、变量名保持准确。
- 代码行过长时按语言习惯换行，不横向溢出。

## 八、链接与引用

- 引用源码时给出真实路径；路径与符号名作为稳定定位依据，行号作为辅助。
- 行号必须来自本轮实读；无法复核时写“未复核”，不编造。
- 引用外部资料时给出可访问来源；不生成未经验证的链接。
- 相对链接指向仓库内真实文件；锚点指向真实标题。
- 不把推测写成源码事实；未确认信息标注“待验证”。
- 链接文字说明目标内容，不使用“这里”“点击”。

## 九、文档元数据

设计文档、实施计划、RCA、评审材料建议在 H1 之后加简洁元数据。接受两种形式：

表格（推荐）：

```markdown
| 项 | 值 |
|---|---|
| 文档类型 | 架构设计 |
| 状态 | 设计中 |
| 适用版本 | <版本> |
| 证据基线 | <commit / 文档 / 未核验> |
| 最后核验 | <YYYY-MM-DD / 未核验> |
```

引用块（适用于文章或项目覆盖层）：

```markdown
> 文档类型：技术原理
> 状态：草稿
> 适用版本：<版本>
> 证据基线：<来源>
> 最后核验：<YYYY-MM-DD / 未核验>
```

要求：

- 必需键：`文档类型`、`状态`、`适用版本`、`证据基线`、`最后核验`。
- 按类型追加：计划加 `计划范围`；RCA 加 `事件日期`、`处置状态`；评审加 `评审对象`、`评审结论`。
- `作者` 仅在已知时填写。
- 未知值写 `待补充` 或 `未核验`；不根据文件时间推断日期，不编造作者、版本、commit 或审批状态。
- 普通技术博客不强制元数据。

## 十、文件与命名

- 文件名使用小写 kebab-case 或项目既有命名；项目归档命名遵循项目技能。
- 一个文件只承载一个文档；不把多篇文档拼在一个文件里。
- 不在正文中使用绝对本机路径；需要时使用仓库相对路径。
- 文档内引用的图片、夹具、脚本使用相对路径，并确保存在。

## 十一、快速自检

- 只有一个 H1？
- 标题层级是否跳级，编号是否连续？
- 表格分隔行与列数是否正确？
- 围栏是否闭合、语言标识是否正确？
- 相对链接与锚点是否存在？
- ASCII 图是否超宽、是否用 Tab、是否有图注？
- 元数据是否完整，是否存在未说明的占位符？
- 是否存在行尾空格或连续多个空行？

可运行 `scripts/doc_lint.py` 做静态检查；它不能替代人工审查。
