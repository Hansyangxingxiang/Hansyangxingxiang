# 已有文档修改规则

修改用户已有文档时，先判断变更类别，再决定权限与保留范围。不得借格式统一改写技术内容。

## 一、四类变更

| 类别 | 典型操作 | 是否改变含义 | 权限与要求 |
|---|---|---|---|
| 格式优化 | 空行、标题层级、编号、表格转义、围栏语言、链接语法、元数据形式 | 不应改变 | 可直接做；用 `doc_lint` 复核；记录范围 |
| 表达优化 | 措辞、句序、术语统一、去冗余 | 不应改变事实 | 保留事实、数字、单位、限定词与作者声音；大段改写先确认 |
| 结构调整 | 章节顺序、合并/拆分、编号迁移、套用模板 | 可能改变阅读路径 | 需用户确认；保留已确认章节与结论；给出旧→新映射 |
| 技术内容变更 | 事实、结论、设计决策、范围、指标 | 会改变 | 必须给依据并由用户决定；与格式修改分开；记录理由与证据 |

判断顺序：先问“是否改变技术含义”。改变即技术内容变更；不改变再看“是否改变章节结构”。

## 二、保留规则

1. 保留已确认的章节与标题，除非用户要求重排。
2. 保留已确认的技术结论、设计决策、数字、单位、条件与不确定性。
3. 不擅自改变方案，不因模板有某一章而补写技术内容。
4. 不删除重要示例、表格、图形与引用；确需删除时说明原因并征得同意。
5. 不把旧文档的 `file:line` 直接沿用；需要时按当前版本重新核对。
6. 不为统一格式而批量重排无关文档。
7. 不把一种文档类型的模板强行套到另一种类型；跨类型结构迁移需用户确认并给出旧→新映射。
8. 不引入未经确认的技术细节；无法确认时保留原文或标“待验证”。

## 三、格式优化流程

1. 备份或确认 Git 状态；不覆盖未提交改动。
2. 用 `--profile legacy` 先跑检查，区分既有问题与本次引入的问题。
3. 只修改格式层；每类修改单独记录。
4. 重新运行 `--profile new`；确认无新增 error。
5. 对比渲染含义；表格列、代码围栏、链接与图注不得改变语义。
6. 输出变更说明：修改类别、文件、范围、未改动项。

## 四、结构调整流程

1. 先给旧→新章节映射与影响说明，等待确认。
2. 保留原文内容，只移动与合并；不借机重写结论。
3. 编号连续，交叉引用同步更新。
4. 图、表、脚注随所属章节移动，图号连续。
5. 完成后说明：合并/拆分/删除/新增了哪些章节，哪些内容未动。
6. 技术内容如需同步修改，另列清单并给出依据。

## 五、技术内容变更流程

1. 指出原文结论、拟修改结论与依据（源码、日志、文档、实验）。
2. 说明影响范围：设计、兼容、测试、已发布文档。
3. 由用户决定是否修改；未获确认时保留原文并标注待确认。
4. 修改后记录：原文、修改后、依据、版本/commit、核验状态。
5. 不与格式修改混在同一段 diff 中，便于审查与回滚。

## 六、交付说明模板

```text
修改类别：格式优化 / 表达优化 / 结构调整 / 技术内容变更
文件：<path>
范围：<章节或全文>
保留：<已确认章节、结论、示例、表格、图形>
变更：<逐项列表>
依据：<证据或用户裁决>
未改动：<明确不动的部分>
未验证：<未运行项>
```

## 七、禁止事项

- 不把“格式规范化”当作重写技术内容的理由。
- 不在未确认时删除用户章节、结论、示例或图形。
- 不根据文件时间推断版本或核验日期。
- 不伪造作者、审批状态、性能数字或实验结论。
- 不对同一文档同时做大规模结构重排与技术结论修改。
