# 技术文档内容组织规范

本文件规定技术文档“写什么、按什么顺序写、如何论证”，不规定具体项目的技术结论。方法与判断仍由领域技能负责。

## 一、面向读者

默认读者是有研发经验的工程师，熟悉基本系统概念，但未必了解本项目。写作目标：

- 让读者理解系统为什么这样设计，而不只是知道有哪些函数。
- 让结论可复核：给出源码、日志、官方文档或实验依据。
- 让边界清楚：正常路径、异常路径、并发条件、限制与代价都能找到。
- 让文档可长期维护：术语稳定，引用可追溯，结构不过度依赖易漂移的编号。

## 二、推荐论证顺序

1. **问题**：现有架构、功能或实现存在什么问题，后果是什么。
2. **目标**：功能目标、非功能目标（性能、可靠性、兼容性）与明确非目标。
3. **约束**：版本、协议、数据兼容、部署形态、资源与运维限制。
4. **架构**：组件、职责、边界、控制路径与数据路径。
5. **机制**：核心数据结构、状态、算法与关键实现。
6. **正常流程**：一次操作如何开始、推进、完成，完成条件是什么。
7. **异常流程**：超时、失败、重试、回滚、部分成功、恢复。
8. **并发与生命周期**：锁、TOCTOU、状态迁移、资源释放、重启与迁移。
9. **取舍**：为什么采用该方案，为什么不采用其他方案，代价与限制。
10. **验证**：如何证明方案正确，哪些已执行、哪些未执行或受阻。

不要求每篇文档覆盖全部条目；按文档类型与实际材料选择，合并相关章节，不机械填充。

## 三、结论与依据

- 重要结论先给结论，再给依据与边界；不把推理过程埋在段落末尾。
- 事实必须可追溯：源码路径 + 符号名，必要时附已验证行号；命令输出；日志；官方文档。
- 行号只作辅助；路径与符号名是稳定定位依据。行号必须来自本轮实读。
- 推断必须标注“推断”，说明依据与不确定性。
- 建议必须标注“建议”，说明取舍与适用条件。
- 未验证内容标注“待验证”，列出验证方法；不把计划中的验证写成已通过。
- 不编造函数名、结构体字段、日志、错误码、实验数据或性能数字。
- “根因”是证据闭环后的结论，不是单条 ERROR 日志或单次现象。

证据标签与通用复用规则以 `references/shared-method.md` 为准；写作类技能可使用更细的分类（如源码事实、官方设计、实验观察），但必须能映射回四级语义。

## 四、技术深度

- 解释机制，不逐行复述源码；源码片段只保留支撑结论的最小片段。
- 从概念到实现逐层推进：对象/模型 → 状态/元数据 → 控制路径 → 数据路径 → 异常与并发。
- 先讲“有哪些东西”，再讲“东西怎么动”；先模型后流程。
- 正常流程与异常流程分开；完成条件与可见性必须明确。
- 讨论性能时给出指标定义、单位、测试条件与数据来源。
- 讨论取舍时同时写收益、代价、适用边界与不采用某方案的原因。

## 五、表达纪律

- 中文正文；英文技术术语保留原文（IO、Block Layer、DISCARD、COW、RBD、NVMe 等），首次出现可加中文注释，之后统一用英文原词。
- 代码标识符、函数名、结构体名保持原文。
- 一个段落一个观点；段落适中，不写超长句。
- 避免模板化开头与宣传语：不写“随着……的发展”“众所周知”“本文将深入探讨”。
- 避免空泛判断：不写“性能显著提升”“大幅优化”而不给指标与条件。
- 避免绝对化：不写“不受影响”“总是”“都”，除非写明前提。
- 不使用 Emoji 代替技术说明；不过度加粗。
- 保留作者的限定词、否定、概率与不确定性；不把“可能”改成“会”，不把“约 10%”改成“10%”。

## 六、结构与模板

- 章节结构由 `templates/` 决定；本文件只规定内容组织原则。
- 模板是默认骨架，不是机械清单；可合并、可裁剪，但不得留下空章节或为凑章节扩写。
- 同一文档内编号风格一致；既有稳定编号优先保留。
- 长文档按“总—分—总”组织：先给总体关系，再分模块展开，最后回到取舍与验证。
- 附录、实现参考、术语表、修订记录可不编号，放在正文之后。

## 七、图表与正文分工

- 表格承载结构化对照：职责、参数、状态、对比、矩阵、风险。
- 正文承载论证：原因、条件、边界、异常与取舍。
- 图承载关系与流程：架构、控制/数据路径、时序、状态、恢复。
- 图必须配图注与正文解释；图不替代论证。
- 同一结论不要在图、表、正文中重复三遍；选择最合适的载体。

## 八、文档类型选择

按任务选择最小充分章节：

| 文档类型 | 必须覆盖 | 可裁剪 |
|---|---|---|
| 架构设计 | 问题、目标/非目标、架构、关键流程、并发、兼容、测试、风险 | 性能、附录 |
| 源码分析 | 目标、版本基线、入口、调用链、数据结构、流程、异常、结论 | 方案、测试 |
| RCA | 现象、影响、时间线、证据、触发链、根因、修复、预防 | 架构全量说明 |
| 性能分析 | 目标、环境、负载、指标、结果、瓶颈、优化、对比、回归 | 架构细节 |
| 技术原理 | 问题、模型、架构、机制、正常/异常流程、取舍、验证 | 具体修复方案 |
| 实施计划 | 背景、范围、现状、方案、任务、依赖、影响、验证、回滚、风险 | 原理全量推导 |

## 九、完成前自检

- 是否回答了“为什么需要这个设计”，而不只是“怎么实现”？
- 关键结论是否有依据，推断与事实是否分开？
- 正常流程、异常流程、完成条件是否齐全？
- 并发、生命周期、资源释放是否检查？
- 取舍是否写明收益、代价与不适用场景？
- 术语是否与项目锚点一致，是否保留了英文原词？
- 是否存在未解释的缩写、未标注的假设、未验证的绝对化结论？
- 结构与模板差异是否说明，是否留下空章节？
