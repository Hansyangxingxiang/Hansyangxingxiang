# ASCII 技术架构图规范

本文件是 ASCII 图的唯一权威源。项目专属角色、组件命名与控制/数据语义由项目仓库的技能补充；本文件不写项目词。

## 一、默认格式

正式技术文档优先使用 ASCII 表示：

- 系统架构与模块关系。
- 控制路径与 IO 数据路径。
- 时序与调用关系。
- 状态机与生命周期。
- 故障恢复、迁移、并发执行关系。

默认不使用 Mermaid。只有以下情况使用 Mermaid：

1. 用户明确要求。
2. 目标平台明确只接受 Mermaid 或有渲染保证。

Mermaid 图不替代文字解释；图中的行为仍须以源码或已确认设计为依据。

## 二、布局规则

1. 布局清晰，组件对齐，尽量对称。
2. 自上而下表示分层；从左到右表示时序或阶段推进。
3. 箭头方向统一，避免双向混用；同步与异步用不同线型或标签。
4. 避免连线交叉；无法避免时拆图。
5. 避免超宽：显示宽度建议不超过 100 列；公众号等窄屏场景不超过 78 列。
6. 使用等宽字符；不使用 Tab 对齐。
7. 图中只保留必要信息；细节放到图后正文。
8. 图后提供文字解释，说明这张图回答的问题、条件与箭头语义。
9. 同一机制不要既画流程图又画时序图；二选一。
10. 不把部署视图、逻辑架构、函数调用层次混在一张图里。

## 三、控制路径与数据路径

分布式存储图必须能区分：

| 路径 | 内容 | 图上表达 |
|---|---|---|
| 控制路径 | 管理请求、元数据更新、状态变更、任务调度 | 细线、虚线和“control/metadata”标签 |
| 数据路径 | 客户端 IO、数据搬运、副本同步、落盘 | 粗线或实线，标注读写方向与数据位置 |
| 异步路径 | 后台任务、恢复、迁移、GC | 虚线 + “async” 标签 |
| 故障路径 | 超时、重试、failover、降级 | 单独图或独立分支，不与正常路径混画 |

要求：

- 不把控制路径画成数据路径，也不把元数据返回画成数据搬运。
- 明确同步/异步；明确请求与响应方向。
- 主副本与从副本之间的交互单独标注。
- 图中角色与实际组件一致；不画不存在的直接调用关系。
- 关键状态变化在图注或正文解释。

## 四、常用骨架

### 4.1 分层架构

```text
┌──────────────────────────────┐
│          Client              │
└──────────────┬───────────────┘
               │ control / data
┌──────────────▼───────────────┐
│        Control Plane         │
└──────────────┬───────────────┘
               │ metadata
┌──────────────▼───────────────┐
│         Data Plane           │
└──────────────────────────────┘
```

图注示例：**图 1：客户端、控制面与数据面的分层关系。** 实线为同步请求，箭头方向为调用方向；未画出异步恢复路径。

### 4.2 控制/数据分离

```text
Client ──control──▶ Control Plane ──metadata──▶ Store
   │                                              ▲
   └──────────────────data────────────────────────┘
```

图注示例：**图 1：控制路径与数据路径分离。** 控制请求不携带数据；数据由客户端直接写入 Store。

### 4.3 时序

```text
Client          Control Plane          Store
  │                   │                  │
  │──1. request──────▶│                  │
  │                   │──2. lookup──────▶│
  │                   │◀──3. location────│
  │◀──4. location─────│                  │
  │──5. data────────────────────────────▶│
  │◀──6. ack─────────────────────────────│
```

图注示例：**图 2：一次写请求的时序。** 步骤 2–4 为控制路径，步骤 5–6 为数据路径；完成条件为收到 ack。

### 4.4 状态机

```text
[Created] ──attach──▶ [Attached] ──detach──▶ [Detached]
                          │                      │
                          └──────delete──────────┴──▶ [Deleted]
```

图注示例：**图 3：对象生命周期。** 箭头为允许的状态转换；未画出的转换视为非法。

## 五、字符与语义

推荐框线字符：`┌ ┐ └ ┘ ├ ┤ ┬ ┴ ┼ ─ │ ▼ ▲ ◀ ▶`。

要求：

- 同一张图只使用一种框线风格（全 Unicode 或全 ASCII `+ - |`），不混用。
- 箭头必须有语义：调用、控制消息、数据流、异步通知分别在图注说明。
- 不用的箭头样式不要出现在同一张图里。
- 对齐以显示宽度为准：CJK 字符占 2 列，组合字符占 0 列。
- 不在 ASCII 图中使用 Tab；用空格对齐。

## 六、图注与正文引用

格式：

```markdown
**图 N：<一句话结论>（<条件/图例>）**
```

要求：

- 图注写出这张图回答的问题，不写“架构图”“流程图”这类空标题。
- 图注说明条件、图例、箭头语义与数据位置。
- 正文首次引用写“如图 N 所示”，不使用“如下图”。
- 图号连续；正文引用每一张图。
- 图是概念示意还是实际实现，必须在图注或正文说明；不把示意当源码事实。

## 七、图后正文解释

重要架构图、调用链图、时序图、状态图或恢复图之后，正文按以下四段解释。允许省略与图无关的部分，但不得省略真实风险。

### 7.1 组件职责

- 说明控制面、数据面、元数据与 IO 各自负责什么，边界在哪里。
- 图中每个组件都应有职责说明；正文中的关键组件也应在图中出现。
- 项目角色使用项目统一名称；无法确认的角色标“待核验”，不用推测补齐。

### 7.2 交互流程

- 写清起点、经过路径、同步或异步、返回或完成条件。
- 复杂流程用编号步骤；步骤与图中箭头一一对应。
- 控制请求、IO 数据请求、元数据操作、异步后台任务分别说明，不混为一条路径。
- 跨组件、跨节点、跨存储设备，或涉及异步回填、恢复的流程，分别解释各段边界。

### 7.3 关键机制

- 说明支撑该流程的关键数据结构、状态迁移、元数据、IO 行为与一致性保证。
- 解释图上看不出的约束：锁、顺序、可见性、重试、幂等、资源释放。
- 写明取舍：为什么这样组织路径，代价是什么，哪些条件不满足时机制不成立。

### 7.4 异常与边界

- 覆盖失败、部分成功、并发、节点故障、超时、重试、降级与恢复。
- 写明容量、协议、版本、部署形态等限制，以及明确不支持的场景。
- 正常路径与异常路径不混画；异常路径若不在图中，正文必须单独说明。

## 八、拆图规则

以下情况拆图：

- 参与者过多导致连线交叉。
- 正常路径与异常路径同时出现。
- 控制路径与数据路径互相遮挡。
- 一张图需要回答两个以上问题。
- 显示宽度超过限制。

拆图后每张图独立可读，图注说明相互关系。

## 九、质量检查

### 9.1 人工检查（脚本不能替代）

- 方框是否对齐，边框是否闭合？
- 箭头方向是否正确，是否存在悬空箭头？
- 组件职责是否清晰，角色是否与实际系统一致？
- 控制流、数据流、元数据操作与异步任务是否混淆？
- 是否存在不必要的交叉或过长连线？
- 是否有图注与图例？
- 图后是否按四段解释：组件职责、交互流程、关键机制、异常与边界？
- 图中每个组件是否在正文有职责说明？正文关键组件是否都在图中？
- 箭头方向是否与实际调用或数据流一致？是否画出了不存在的直接调用？
- 同步/异步、返回方向、完成条件是否明确？
- 是否存在只有图、没有正文解释的流程？
- 正常路径与异常路径是否分开？真实风险是否被省略？
- 图、正文、术语、项目角色命名是否一致？未验证关系是否被画成事实？

### 9.2 静态可检查项

`scripts/doc_lint.py` 只能检查：

- ASCII 围栏的显示宽度是否超限。
- 是否使用 Tab。
- 是否混用 Unicode 与 ASCII 框线。
- 是否缺少图注。
- 是否出现 Mermaid（提示确认是否显式要求）。

脚本**不能**验证架构的技术正确性、控制/数据语义、组件职责、对称性与可读性；这些必须人工审查。
