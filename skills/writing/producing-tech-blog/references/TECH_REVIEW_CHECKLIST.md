# 技术审校清单

配套 `producing-tech-blog`。机器检查跑 `scripts/blog_lint.py`，本文件负责机器查不出来的部分。

## 一、缺陷分级

| 级别 | 定义 | 处理 |
|---|---|---|
| P0 | 事实错误、源码/数据造假、敏感信息泄露、编码乱码 | 阻塞发布，必须清零 |
| P1 | 结构缺陷（缺取舍/缺结论）、逻辑矛盾、图与正文不一致、标题党 | 必须修 |
| P2 | 表达啰嗦、AI 味、排版细节 | 尽量修，可带病发布 |

结论只有两种：**可发布** / **需修复后重跑**。不存在"基本可以"。

## 二、技术准确性（12 项，逐条打勾）

- [ ] 1. 技术概念定义与主流共识一致，没有自造术语冒充通用概念
- [ ] 2. 架构描述与目标版本一致（不是把两个版本的架构混着讲）
- [ ] 3. 调用链每一跳都能在代码里找到；函数名、文件名拼写正确
- [ ] 4. 代码片段可编译/可运行，或明确说明是节选并给出省略内容
- [ ] 5. 命令与参数在目标版本有效（不存在的 flag 不许出现）
- [ ] 6. 配置文件字段名、单位、默认值正确
- [ ] 7. 性能数据有环境、有基线、有原始输出
- [ ] 8. 数字换算正确（KiB/GiB/s、IOPS 与带宽的关系）
- [ ] 9. 官方事实与个人判断已区分（"文档说…" vs "我的判断是…"）
- [ ] 10. 未验证内容已标注，未写成结论
- [ ] 11. 引用来源可访问、版本与日期齐全
- [ ] 12. 跨版本差异有说明，没有把旧版本行为当现状

常见 P0 陷阱：把 `p99` 写成均值、把 `4 KiB` 与 `4 KB` 混用、把"官方支持"写成"实测通过"、把社区 issue 的猜测当作官方结论。

## 三、架构与逻辑（8 项）

- [ ] 1. 有一句话能说清的"本文解决什么问题"，且全文围绕它
- [ ] 2. 章节顺序符合"背景→原理→架构→实现→取舍"，没有倒置
- [ ] 3. 上一节的问题在下一节被回答，不出现悬空问题
- [ ] 4. 控制面与数据面分开讲，没有混成一条线
- [ ] 5. 故障路径至少讲了一条（超时/掉线/回滚）
- [ ] 6. 有"设计取舍"章节，且写了放弃了什么、什么条件下要改
- [ ] 7. 全文无自相矛盾（同一参数前后描述一致）
- [ ] 8. 结论是由前文证据推出来的，不是突然出现的

## 四、内容价值（8 项，防水文）

- [ ] 1. 目标读者已掌握的基础没有大段科普（≤3 行带过）
- [ ] 2. 每个建议都有"是什么/为什么/怎么做"三层，不只停在概念
- [ ] 3. 有具体工具、命令、参数、配置（不是"可以用工具分析"）
- [ ] 4. 有踩坑细节（只有做过才知道的那种）
- [ ] 5. 有量化标准（延迟阈值、队列深度、副本数）
- [ ] 6. 至少 1–2 个"反常识但有证据"的判断
- [ ] 7. 同一观点只出现一次，没有换个说法重复
- [ ] 8. 删掉任意一节，读者会真的少拿到东西

## 五、可读性与风格（8 项）

- [ ] 1. 开头第一句是事实/问题，不是"随着…的发展"
- [ ] 2. 段落 ≤4 句，超长段已拆分
- [ ] 3. 无"值得注意的是/综上所述/说到底/不是A而是B"等 AI 味句式
- [ ] 4. 无三项以上同构排比，无营销词
- [ ] 5. 术语首次出现给中英对照，全文译名统一
- [ ] 6. 代码块都有语言标注，前后都有解释句
- [ ] 7. 图都有图注，正文有"如图 N"引用
- [ ] 8. 结尾是 3–5 条判断 + 一个开放问题，不喊口号

## 六、合规与脱敏（10 项，P0 级）

公开稿逐条检查，命中任一项即停：

- [ ] 1. 无公司名称、内部产品名、内部项目代号（含缩写、拼音、代号变体）
- [ ] 2. 无内部代码仓库地址、内部 GitLab/Gerrit 链接、commit hash 指向私有库
- [ ] 3. 无客户名称、客户场景可识别信息（行业+规模+地域的组合也可能识别）
- [ ] 4. 无内网 IP、主机名、域名、VLAN/网段、账号、口令、token、证书
- [ ] 5. 无网络拓扑、机房位置、机架/供电/带宽等物理信息
- [ ] 6. 无未公开的产品架构、协议细节、私有 API、性能指标
- [ ] 7. 未直接复制内部设计文档（含图表、表格、原文段落）
- [ ] 8. 未把公司私有实现描述成某开源项目的官方实现
- [ ] 9. 截图已打码（终端提示符含主机名/IP 的也算）
- [ ] 10. 实验环境是自建的，或已说明为公开资料

可保留：通用技术原理、公开开源项目源码、公开文档、自建实验环境、已脱敏的通用工程经验、经过验证的个人判断。

脱敏改写示例：

| 原始 | 公开稿 |
|---|---|
| 我们在 某分布式块存储系统 上把快照延迟压到 3ms | 在某分布式块存储系统上，快照延迟压到 3ms（内部实现细节略） |
| 客户 A 的 200 节点集群 | 一个 200 节点规模的集群 |
| 192.0.2.10 上的 OSD 掉线 | 某个 OSD 节点掉线 |
| 内部方案：先写日志再写数据 | 一种常见做法是先写日志再写数据（不指向具体产品） |

发现疑似敏感内容的处理：**先提醒用户确认，不直接输出发布稿**；给出"可发布版本 + 待确认项清单"两段，让用户决定。

## 七、公众号排版（8 项）

- [ ] 1. 正文字号 15–16px，行高 1.7–1.9，段间距一致
- [ ] 2. 标题层级不跳级，同级样式统一
- [ ] 3. 代码块可横向滚动，长行不折成麻花
- [ ] 4. 表格列数 ≤5，手机端不横向溢出
- [ ] 5. 图片居中、有图注、宽高比正常（未被拉伸）
- [ ] 6. 强调色只用一种（`#1677FF`），没有彩色满天飞
- [ ] 7. 引用块只用于核心结论，全文 ≤3 处
- [ ] 8. 全文首屏（前 3 屏）能看出"这篇讲什么、值不值得读"

## 八、10 维打分（终审）

每维 1–10 分，总分 100。**≥80 且无单项 <8 才可发**。

| 维度 | 8 分标准 |
|---|---|
| 受众匹配 | 内容深度与目标读者认知对齐，不劝退也不哄小孩 |
| 阅读体验 | 节奏有起伏，长段与图/码交替 |
| 信息密度 | 有效信息占比高，删掉任何一段都可惜 |
| 技术准确性 | 断言可溯源，无 P0 |
| 时效性 | 版本与状态是最新的，过时内容已标注 |
| 实操性 | 读者能照着做，命令可复制 |
| 原创洞察 | 有 1 处以上"只有做过才知道"的判断 |
| 结构逻辑 | 问题链完整，结论有落点 |
| 数据可信 | 数字有环境、有基线、有来源 |
| 传播力 | 有具体分享理由（不是标题党） |

打分要写一句理由，不只给分数：

```
技术准确性 9 — 调用链逐跳核对过 v1.7.2 源码；性能数据只有单次，扣 1 分
传播力 8 — "队列深度不是越大越好"有反直觉点，标题可再具体
```

## 九、发布前 60 秒快检

1. 标题能被正文兑现吗？
2. 开头三行有具体信息吗？
3. 有没有一处"只有我能写"的内容？
4. 所有数字都有来源/环境吗？
5. 有没有公司名、客户名、内网地址？（搜索 `内网`、`公司`、`客户`、点分十进制）
6. 代码块都标语言了吗？
7. 每张图都有图注吗？
8. 结尾给了读者一个可讨论的问题吗？
