# Writing Project Principles — 项目技术原理写作

## Overview

把开源基础设施项目的实现讲成可长期阅读的技术原理：读者看完应能回答系统维护哪些状态、数据在哪里、请求经过哪些组件、何时算完成、失败或并发时靠什么保持正确、性能收益来自哪里又支付了什么代价。

核心链条是**问题 → 组件与数据 → 证据 → 设计取舍 → 验证**。文章以源码、官方文档、论文和实验为依据，但不写成逐函数导读；设计动机可以分析，但必须与已实现行为、可选配置、论文架构分开。

本技能只放通用流程与判断标准。结构、证据、图示的细节按需读取 `references/`；项目差异读取 `references/<project>.md`，不要把某个项目的术语写进主技能。

## When to Use / NOT

**Use**：
- 规划一个项目的技术原理系列：范围、篇目、每篇核心问题、实验边界。
- 写指定主题的单篇文章：架构、数据模型、Put/Get、生命周期、故障恢复、性能机制等。
- 评审或修改已有文章：技术结论、证据链、结构、图示、可读性。
- 检查系列一致性：术语、组件命名、版本锚点、架构结论、性能数字、图示语义。

**NOT**：
- 以逐函数讲解为主的源码阅读笔记 → `storage-code-analysis`
- 生产故障排查、空间未释放、性能异常定位 → `storage-debug`
- 新功能方案设计、技术选型 → `design-document`
- 公众号内容选题与表达 → `wechat-tech-article`；微信 HTML 排版 → `producing-tech-blog`
- NeonSAN 专属原理规范 → `writing-neonsan-internals`（personal-notes 仓库维护）
- 未经请求的代码修改、集群部署、远端变更或文章发布

## 模式路由

| 任务 | 先读 | 工作流 | 产出 |
|---|---|---|---|
| 系列规划 | 项目配置 + `assets/series-plan-template.md` + `references/article-structure.md` | 定范围与证据基线 → 拆每篇核心问题 → 填计划表 → 标实验边界 | 系列计划文件 |
| 单篇写作 | 项目配置 + `references/article-structure.md` + `references/evidence-rules.md` + `references/diagram-guidelines.md` + `assets/article-template.md` | 五步工作流 | 文章草稿 + 独立作者记录 |
| 文章评审 | `references/article-structure.md` 的评审清单 + `references/evidence-rules.md` | 逐条标证据类别 → 指出越界结论 → 给修改建议 | 评审报告或修订稿 |
| 系列一致性检查 | `references/article-structure.md` 的一致性矩阵 + 已有系列计划 | 建术语/结论/版本对照 → 列冲突 → 给统一建议 | 冲突清单 |

先判断任务类型再动笔。系列规划阶段不写正文；评审任务默认不改写全文，除非用户明确要求。

## 五步工作流

1. **明确任务范围**
   - 判断是系列规划、单篇写作、评审还是一致性检查。
   - 优先复用用户已给的项目、受众、版本和环境信息。
   - 缺少非关键信息时作合理假设并注明；只有缺失信息会实质改变结论时才提问。
2. **固定证据基线**
   - 记录项目仓库、tag/commit、文档版本、相关依赖版本。
   - 本地源码优先；外部资料优先官方文档、原始论文、官方仓库。
   - 区分论文架构、当前实现、可选配置、历史行为；issue、RFC、未合并 PR 不算已实现。
   - 无法获取关键源码时说明局限，输出原理草稿或待验证项，不伪装成已完成源码分析。详见 `references/evidence-rules.md`。
3. **建立机制认识**
   - 识别组件职责、控制路径、数据路径、部署关系。
   - 明确数据在哪里、谁管理、何时可见、何时释放。
   - 沿主流程追踪必要调用链，不按目录逐文件复述。
   - 按主题检查并发、失败、重试、回收和恢复，不死板罗列。
4. **组织文章**
   - 每篇回答一个核心问题；先场景与机制，再引入必要代码。
   - 解释设计取舍、适用条件和代价。
   - 配置与命令必须对应所分析版本；实验只用于验证关键结论。结构见 `references/article-structure.md`。
5. **自检并交付**
   - 检查技术结论、证据、图文一致性和阅读体验。
   - 正文与作者分析记录分开保存。
   - 更新项目已有的系列计划和术语记录，避免重复创建。
   - 不自动发布文章，不自动执行远端或集群变更。

## 证据基线摘要

四类证据必须可区分：**源码事实 / 官方设计说明 / 实验观察 / 作者推断**。关键实现结论要能追溯到固定版本的文件、符号和必要代码位置；源码链接优先用 commit 永久链接。不编造函数、参数、返回值、日志、结果和性能数字；未运行的实验标为「验证方案」。

配置文件里的内容只是规划约束，不是已验证的实现事实；动笔前重新固定版本并核验。

## 默认文章结构

默认五段：**问题与场景 → 核心原理 → 工作过程 → 边界与异常 → 实验与结论**。这是默认结构，不是机械模板：架构篇突出组件与路径，生命周期篇突出状态与转换条件，性能篇突出模型、瓶颈与实验方法，简单主题可合并章节。默认约 2500–4000 中文字，按复杂度调整；技术事实准确优先于字数。

## 图示

默认 Mermaid，每篇通常 2–3 张核心图。一张图只解释一个主要问题；控制信息与实际数据流明确区分；标注关键数据位置（GPU HBM、host DRAM、remote DRAM、SSD）；系列内组件名、方向和配色语义一致。不混用部署视图、逻辑架构与函数调用层次。用户指定 ASCII 等格式时遵循用户要求。详见 `references/diagram-guidelines.md`。

## 项目配置

写作或规划前，先确认项目，再读取 `references/<project>.md`。当前首个配置是 `references/mooncake.md`，内容包括系列名、范围、建议篇目、实验条件与声明边界。

项目配置是**规划约束**，不是未经核实的实现事实。接入新项目时复制同样的结构新建参考文件，主技能不改。

## 与已有技能协作

| 技能 | 谁做什么 | 交接点 |
|---|---|---|
| `storage-code-analysis` | 深入读源码、下调用链结论 | 其分析结果作为本技能的证据输入 |
| `wechat-tech-article` | 面向读者的公众号内容与表达 | 本技能完成原理内容后，按需再重组 |
| `producing-tech-blog` | 微信 HTML 排版 | 只有用户要求排版时进入 |
| `humanizer-zh` | 语言润色、去 AI 味 | 发布前按需调用 |
| `writing-neonsan-internals` | NeonSAN 专属原理文档规范（personal-notes 仓库维护） | NeonSAN 任务优先用它 |

协作技能存在时按职责分工，避免重复实现；不存在时完成本技能的核心工作，不虚构调用成功。只有用户明确要求公众号版本或发布排版时，才进入后续流程。

## 交付自检

- [ ] 版本锚点（仓库、tag/commit、文档、依赖）明确且与正文一致
- [ ] 关键结论可追溯到文件/符号/代码位置，或明确标为推断
- [ ] 四类证据没有混写；issue/RFC/未合并 PR 未被当作已实现
- [ ] 未运行实验标为「验证方案」，假设数据未被写成实测结果
- [ ] 没有编造的函数、参数、日志、结果或性能数字
- [ ] 每篇只有一个核心问题，没有空章节或机械填充
- [ ] 图示一图一问题，控制流与数据流、概念模型与实现没有混淆
- [ ] 术语、组件名、图示语义在系列内一致
- [ ] 待验证项与关键未知单独列出，没有混入确定结论
- [ ] 正文与作者分析记录分开；未自动发布或执行远端变更

## Common Mistakes

- 写成「什么是 X」式科普，没有从问题推进到机制与取舍。
- 把局部行为泛化为所有协议、后端或部署模式。
- 根据函数名推断完整行为，或只读函数不看调用上下文。
- 把设计文档、论文架构或未合并 PR 当作当前实现。
- 注释与实现冲突时跟着注释走，而不是看控制流。
- 编造日志、返回值、实验现象或性能数字。
- 用「Put 成功」直接证明走了远端 RDMA，缺少位置与传输证据。
- 同一机制既画流程图又画时序图，或一张图塞进多层视图。
- 跨篇术语漂移，英文技术词被翻译成不同中文说法。
- 评审时直接重写全文，掩盖了证据缺陷而不是指出它。
