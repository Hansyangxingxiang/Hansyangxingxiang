# 文章结构与评审参考

> 本文件是 `writing-project-principles` 的结构与检查参考。
> 先判断文章属于哪一类，再选骨架；五段是默认结构，不是机械模板。

## 一、默认五段结构

| 段 | 回答什么 | 必须覆盖 | 常见误区 |
|---|---|---|---|
| 1. 问题与场景 | 这篇解决什么真实问题，读者为什么需要它 | 具体场景、触发条件、本篇核心问题、范围与非目标 | 从「什么是 X」开始；问题大到无法在一篇内回答 |
| 2. 核心原理 | 系统靠什么机制解决这个问题 | 组件职责、核心对象与状态、数据与元数据位置、关键约束 | 只讲功能不讲机制；把设计文档当实现 |
| 3. 工作过程 | 一次操作如何发生、何时算完成 | 控制路径、数据路径、顺序与完成条件、可见性 | 按目录逐文件复述；没有完成点 |
| 4. 边界与异常 | 失败、并发、超时、重启时为什么仍然正确或哪里会坏 | 部分成功、重试幂等、并发协调、回收、恢复、降级边界 | 只写正常流程；用绝对化结论替代前提 |
| 5. 实验与结论 | 哪些结论被验证、哪些仍是推断 | 实验目的、环境、方法、观察、结论、未验证项 | 为凑结构做无意义实验；把未运行的实验写成结果 |

### 五段之间的关系

- 第 1 段建立问题，不展开实现。
- 第 2 段先给模型，再给流程；读者要先知道「有哪些东西」，再理解「东西怎么动」。
- 第 3 段只保留回答核心问题所必需的调用链，代码片段服务于机制解释。
- 第 4 段是原理文章与功能说明的分水岭：没有并发与失败，就没有真正的机制解释。
- 第 5 段回到开篇问题，明确哪些是事实、哪些是实验、哪些仍是待验证。

## 二、按主题调整

| 类型 | 结构重点 | 可合并/拆分 |
|---|---|---|
| 总体架构篇 | 组件、职责、部署边界、控制路径与数据路径 | 可把「工作过程」压缩为路径总览，异常留给专题篇 |
| 数据模型篇 | 对象、标识、关系、地址或索引规则、生命周期 | 可把「边界与异常」并入生命周期 |
| 生命周期篇 | 状态集合、状态转换条件、可见性、释放时机 | 用状态图替代部分文字流程；异常单列 |
| 一次操作篇（Put/Get 等） | 入口、阶段、完成点、可见性、失败分支 | 正常流程与异常分开画图 |
| 性能篇 | 性能模型、瓶颈假设、实验方法、结果与代价 | 「核心原理」突出成本模型；结论必须带实验条件 |
| 对比篇 | 共同问题、方案差异、适用条件、代价 | 用对照表替代重复叙述，避免逐项罗列功能 |

简单主题可以合并章节；不要为了凑五段保留空章节或过细标题。

## 三、分析深度问题库

按主题选择相关问题，不要求每篇全部回答：

1. 操作成功承诺了什么？不承诺什么？
2. 写入什么时候对其他客户端可见？
3. 数据和元数据分别存在哪里？
4. 缓冲区由谁申请、持有和释放？
5. 读取与删除、淘汰、写入并发时如何协调？
6. 部分成功和超时如何处理？
7. 重试是否幂等？
8. 节点退出或进程重启会丢失什么？
9. 有哪些恢复路径与降级边界？
10. 性能收益来自哪里，又支付了什么成本？
11. 哪些行为是所有后端共有，哪些只适用于某个协议或部署模式？
12. 哪些结论来自源码，哪些来自文档、论文或实验？

把问题映射到五段：1–3 主要落在「核心原理」，4–7 落在「工作过程」与「边界与异常」，8–10 落在「边界与异常」与「实验与结论」，11–12 贯穿全文的证据标注。

## 四、单篇写作纪律

- **一篇一个核心问题**：标题与开篇问题一致，正文不跑题。
- **先场景后代码**：代码只用于解释决定行为的机制，不粘贴大段实现。
- **事实优先于字数**：默认 2500–4000 中文字，按复杂度调整；不为凑字数扩写背景。
- **术语写法**：英文技术词保留原文（KV Cache、RDMA、DRAM、SSD、eviction），首次出现解释中文含义，之后统一用法。
- **配置与命令**：必须对应所分析版本；无法确认版本时标注「待核对」。
- **实验**：只做能验证关键结论的实验；环境、步骤、观察分开写；未运行标「验证方案」。
- **作者记录分离**：源码地图、核验过程、放弃的假设、待查问题放在独立作者记录或文末「实现参考」，不混入正文论证。

## 五、评审清单

### 技术结论
- [ ] 每条关键结论能指出证据类别
- [ ] 源码结论能追溯到固定版本的文件与符号
- [ ] 没有把设计文档、论文架构、可选配置或历史行为当作当前实现
- [ ] 没有从函数名推断完整行为，没有把局部行为泛化
- [ ] 注释与实现冲突处已按控制流处理并说明

### 证据与数据
- [ ] 没有编造函数、参数、返回值、日志、结果或性能数字
- [ ] 未运行实验标为「验证方案」
- [ ] 假设数据与实测数据分开标注
- [ ] 关键未知项单独列出，没有混入确定结论

### 结构与表达
- [ ] 每篇只有一个核心问题，开篇承诺在正文兑现
- [ ] 先模型后流程，正常流程与异常分开
- [ ] 没有空章节、过细标题或机械填充
- [ ] 结论带前提，没有「总是」「都」「不受影响」式绝对化表述

### 图示
- [ ] 一图一问题，图注写出它回答的问题
- [ ] 控制信息与数据流可区分
- [ ] 关键数据位置已标注
- [ ] 没有混用部署视图、逻辑架构与函数调用层次
- [ ] 概念模型与实际实现已说明

### 阅读体验
- [ ] 段落不过长，一段一个意思
- [ ] 术语前后一致，英文技术词未被随意翻译
- [ ] 图表与正文互相引用，没有孤立图
- [ ] 结尾回到开篇问题，给出边界与待验证项

## 六、系列一致性检查矩阵

逐项对照系列内所有文章，记录冲突与统一建议：

| 维度 | 检查什么 | 冲突示例 | 处理 |
|---|---|---|---|
| 术语 | 同一概念是否只有一个中文写法与英文原词 | 一处写「副本」，一处写「拷贝」 | 以术语锚点表为准，统一并补首次定义 |
| 组件名 | 组件、进程、角色名称是否稳定 | 一处写 Master，一处写元数据服务 | 选定一个正式名，别名只在首次出现时说明 |
| 版本锚点 | 各篇的 tag/commit、文档版本是否一致 | A 篇 v0.3，B 篇 main | 统一锚点；确需跨版本时显式标注 |
| 架构结论 | 数据/元数据路径、职责边界是否互相矛盾 | 一篇说 Master 不碰数据，另一篇说 Master 中转 | 回到源码核验，统一结论并说明证据 |
| 性能数字 | 数字是否有环境、版本、方法 | 只有数字没有实验条件 | 补条件；无法补齐则删除或标「未验证」 |
| 图示语义 | 同一组件、箭头、颜色是否含义一致 | 实线在一篇表示数据流，另一篇表示控制流 | 在系列计划中固定图例语义 |
| 交叉引用 | 是否依赖易漂移的篇号而非稳定链接 | 「见第 3 篇」 | 改用标题链接或稳定锚点 |

仅请求一致性检查时交付冲突清单与建议，不默认批量改写。用户已明确要求修订时，在授权范围内直接修改，无需重复确认；超出该范围的批量改写先说明影响并确认。

## 七、系列计划的最小字段

系列计划至少包含：系列名、目标读者、范围与非目标、证据基线、文章表（标题、核心问题、前置、证据、图示、实验、状态）、术语锚点表、实验能力与声明边界、更新记录。模板见 `assets/series-plan-template.md`。
