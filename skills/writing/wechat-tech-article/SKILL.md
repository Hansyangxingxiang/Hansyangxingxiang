# WeChat Tech Article — 内容质量与风格

## Overview

本 skill 管**内容质量与风格**，不含排版。产出：内容草稿 + 检查结果。排版（微信 HTML）交接 producing-tech-blog，去 AI 味交接 humanizer-zh。

收到原理文章任务时，先区分机制论证与公众号表达：机制、证据及系列规划由 writing-project-principles 主导；已有技术内容只需标题或读者表达时直接在本技能处理，保留上游证据和技术限定，不重复研究。

核心原则：**技术专家的"翻译官"**——不降级技术深度，只重新组织，让读者能跟上、能记住、能带走。

## 1. 选题能力

### 七类选题
1. **问题类**：真实工程问题（"删除文件后 SSD 空间为何没释放"）
2. **原理类**：机制原理（"DISCARD 到底怎么工作"）
3. **源码类**：源码解读（"BlueStore 的 discard 实现"）
4. **架构类**：架构设计（"RBD 的 IO 路径"）
5. **实践类**：踩坑/调优（"生产环境 discard 配置"）
6. **对比类**：方案对比（"ext4 vs xfs 的 discard 策略"）
7. **趋势类**：技术趋势（"NVMe 与存储栈演进"）

### 取舍标准
选题必须满足：**有问题、有冲突、有认知差异、有实践价值**。至少占两项才值得写。

## 2. 标题设计

### 六型标题
1. **问题型**："删除文件后，SSD 空间为什么没释放？"
2. **原理型**："DISCARD 的完整旅程：从 ext4 到 NVMe"
3. **源码型**："读 BlueStore 源码：discard 到底做了什么"
4. **架构型**："RBD 的 IO 路径：一次写请求的完整旅程"
5. **实践型**："生产环境 TRIM 配置踩坑记"
6. **对比型**："ext4 vs xfs：谁更会发 DISCARD？"

### 标题纪律
- **准确不标题党**：标题承诺的内容，正文必须兑现
- 具体 > 抽象：有数字、有对象、有冲突
- 需要拟标题时给出少量候选；用户已有标题且未要求调整时直接沿用

## 3. 文章结构

### 按文章类型选择结构

沿用用户已有结构。短篇问题解释可用“问题→机制→结论”，源码长文可用“背景→关键路径→证据→验证”，实践文章可用“环境→步骤→结果→限制”。下列十项是可选素材清单，不要求每篇凑齐；无源码或实验时说明边界，不编造章节内容。

### 长文可选结构
1. 开头（钩子）
2. 问题背景
3. 为什么容易搞错
4. 核心概念
5. 架构/层次
6. 协议/数据结构
7. 源码分析
8. 运行过程
9. 实验/验证
10. 总结与延伸

### 开头按需简要交代
- **为什么值得看**：读者为什么要花时间
- **问题是什么**：一句话说清
- **为什么容易搞错**：常见误解/认知差异
- **本文解决什么**：承诺 + 边界

## 4. 技术深度

逐层解释，每层都要讲清楚：
```
概念 → 架构 → 协议 → 数据结构 → 源码 → 运行过程 → 实验
```

- 每层回答：这一层做什么、输入输出、与上下层如何衔接
- 深度到哪层由读者决定：读者是存储工程师，可以深，但每层都要有"为什么"

## 5. 源码分析标准

- **四要素**：位置（`file:line`）/ 关键函数 / 意图 / 运行路径
- **区分源码事实与推测**：源码里写了什么（事实）vs 行为是否符合预期（推测）
- 每个引用带 `file:line`，不信任记忆中的行号
- 代码按完整语义截取，优先短小；伪代码明确标注，不冒充原始实现

## 6. 事实 / 分析 / 观点分离

- **事实**：可验证的源码、日志、数据、文档，带出处
- **分析**：基于事实的推理，标注"推测/推断"
- **观点**：个人判断，标注"我认为/建议"
- 文章里三者清晰，读者能分辨

## 7. 引用与资料研究

- 官方文档、源码、设计文档、RFC、社区讨论
- 每个引用可追溯：链接、`file:line`、issue 编号
- 不引用无法验证的内容

## 8. 原创性

- **重新组织知识**：把已知知识用自己的逻辑重新组织，不翻译、不拼接、不复制
- 有个人视角：为什么这么理解、踩过什么坑、怎么取舍
- 引用他人内容必须标注来源

## 9. 公众号阅读体验

- **短段落**：2-5 行一段，一段一个意思
- **小标题清晰**：读者扫标题能看懂结构
- **代码适量**：按完整语义选取必要片段，伪代码明确标注
- **图文结合**：关键关系难以用文字解释时配自包含图，不规定数量；图形形式遵循项目和目标平台约定
- **重点突出**：关键结论加粗，不滥用

## 10. 系列文章

- **独立成篇**：每篇可单独阅读，不依赖前篇
- **前后关联**：系列内互相引用，标注"见系列第 N 篇"
- **避免重复**：完整概念解释集中一处，后续提供足够独立阅读的简述并引用详解

## 11. 发布前检查清单

### 技术类
- [ ] 所有 `file:line` 有当前版本核验记录，变化部分已重新验证
- [ ] 事实/分析/观点清晰分离
- [ ] 无凭记忆下的源码结论

### 内容类
- [ ] 开头回答"为什么值得看/问题是什么/为什么容易搞错/本文解决什么"
- [ ] 标题承诺的内容正文兑现
- [ ] 每层技术深度讲清楚"为什么"

### 阅读类
- [ ] 短段落、小标题清晰
- [ ] 代码片段语义完整，伪代码与原始代码区分
- [ ] 必要图示自包含，未为凑数量增加图
- [ ] 重点突出不滥用

### 原创类
- [ ] 重新组织而非翻译/拼接/复制
- [ ] 引用他人内容标注来源

## 12. 与 producing-tech-blog 分工

- **本 skill**：产出"内容草稿 + 检查结果"，到此为止
- **producing-tech-blog**：排版成微信 HTML（`.md` 源稿 + 内联 CSS `.html`）
- **humanizer-zh**：需要去 AI 味时在发布前调用

## 输入、交付与证据复用

- 输入：资料、目标读者、文章目的、已有草稿与项目约定。
- 交付与完成条件：内容草稿与检查结果。标题承诺有对应论证，事实有来源，缺少源码或实验时明确限制；随后按需润色、排版。
- 输入不足时先完成有依据的部分，仅询问影响结论或执行的关键缺口。
- 交接证据包含仓库、commit、文件或符号、结论与验证状态。同一版本且相关文件与运行条件未变化时复用已核验记录；版本、文件或关键条件变化时重核相关结论，不重复开展全部研究。
