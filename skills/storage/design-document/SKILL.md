# Design Document — 通用研发技术设计文档专家

## Overview

本 skill 解决"一个研发需求 / 技术问题 / 源码分析结果，如何形成一份完整、合理、可评审、可实现、可测试的研发设计文档"。核心产出是**按改动规模选择轻量或完整模式**的结构化中文方案文档，每条结论带出处。

设计文档是**决策记录**：记录"为什么这么做"（决策）、"怎么做的"（设计）、"不做什么"（非目标）、"有什么风险"（开放问题）。

## When to Use

- 新模块设计
- 功能改造
- 技术选型
- 架构评估
- 需要产出结构化中文方案文档

Not for 源码分析（storage-code-analysis）或排障（storage-debug）。NeonSAN 落盘交接 neonsan-docs。

## 核心方法（先分析，再设计）

- **现状 → 问题 → 约束 → 需求 → 设计**：先讲清楚现状与问题，再谈需求，最后才进入设计。
- **设计必须基于事实**：有源码先分析源码（`file:line` 实读），无源码明确标注假设，不凭空猜测。
- **区分"当前实现"与"目标实现"**、区分"需求"与"实现"。
- **优先异常路径**：成功 / 失败 / 超时 / 重试 / 重复 / 节点故障 / 重启 / 升级 / 回滚。
- **分布式存储必须主动检查数据生命周期关系**：Write / Discard / Snapshot / Clone / COW / Metadata / Recovery。
- **避免过度设计**：每个抽象 / 接口 / 配置项都要能说明"为什么需要它"。

## 选择文档规模

沿用用户现有结构。局部小改动采用轻量模式：问题与范围、方案与取舍、兼容与风险、测试与验收。涉及协议、持久化元数据、跨节点状态机或复杂并发时采用完整模式。轻量模式仍须覆盖适用的异常路径与数据安全约束，不填充无关章节。

## 默认 8 个一级章节（完整模式骨架）

```
1. 背景与目标        — 为什么做：背景/问题/现有限制/改造原因/目标/范围/明确不做
2. 需求分析          — 需要什么能力：2.1 功能 / 2.2 性能 / 2.3 兼容性 / 2.4 配置与运维
3. 总体设计          — 怎么实现：3.1 整体架构(ASCII 图) / 3.2 核心流程 / 3.3 核心设计原则
4. 详细设计          — 每模块怎么实现：数据结构/状态/请求处理/接口/生命周期/错误/重试/资源
5. 数据一致性与并发设计 — Write/Discard/Snapshot/Clone/COW/元数据/重试/超时/故障/重启 的并发检查
6. 兼容性与升级      — 版本兼容(Old↔New)/数据兼容/配置兼容/升级/回滚
7. 监控、测试与验收  — 监控指标/功能/并发/异常/性能测试 + 可执行验收标准
8. 风险与遗留问题    — 风险/已知限制/遗留问题/后续规划（不虚构）
```

**明确约束**：默认不超过 8 个一级章节；复杂功能用二/三级章节，不为"完整"机械增加一级章节。避免过度拆分（如 18 章示例）。

## 章节职责要点

### §1 背景与目标
- 问题、后果链、影响范围、改造原因。
- 目标：功能目标 + 非功能目标（性能、可靠性、兼容性）+ 成功标准。
- 范围与明确不做（非目标 + 原因）。
- **不提前展开实现细节**。

### §2 需求分析
- 只讲"需要什么"，不进入代码实现。
- 功能 / 性能 / 兼容性 / 配置与运维四个维度。

### §3 总体设计
- 架构图默认 ASCII。
- 明确同步/异步、顺序/并发、一致性模型、幂等、错误处理、重试、资源控制。
- 被否方案及原因、最终选择 + 理由（先讲为什么，再讲怎么做）。

### §4 详细设计
- 按实际系统动态划分模块，不机械套模板。
- 涉及源码修改必须结合源码分析，不凭空猜测。
- 接口 / 数据结构 / 流程，覆盖错误路径、并发/锁、兼容性、监控配置。
- 关键结论带源码出处（`file:line`），不信任记忆中的行号。

### §5 数据一致性与并发设计
- 对每个关键并发场景回答 10 问：谁先谁后 / 是否真并发 / 如何同步 / 是否需锁 / 锁粒度 / IO 顺序 / 避免错误释放 / 重复执行安全 / 失败恢复 / 最终一致性。
- 空间回收 / Discard / COW / Snapshot 优先分析数据生命周期。

### §6 兼容性与升级
- 版本兼容：Old Client→New Storage / New Client→Old Storage。
- 数据兼容：老 Volume / 老元数据 / 新增字段 / 默认值。
- 升级前中后 / 失败；回滚（新→老 / 部分节点 / 中途失败 / 数据可回滚）。

### §7 监控、测试与验收
- 监控指标。
- 功能 / 并发（Write+Write、Write+Discard、Discard+Discard、Write+Snapshot、Discard+Snapshot）/ 异常 / 性能测试。
- 验收标准尽量可执行、可判定。

### §8 风险与遗留问题
- 遗留风险、已知边界、待决策项、后续规划。
- 明确标注哪些是"明确不修"（记录用户裁决原文）。
- **不虚构风险**。

## 与其他 Skill 协作

- **storage-code-analysis**：源码 / 调用链 / 数据流分析 → 现状分析 → design-document → 设计方案。
- **storage-debug**：故障 → 根因 → design-document → 修复设计。
- **neonsan-docs**：设计内容按 NeonSAN 规范整理 / 归档 / 落盘。
- 明确：design-document **不依赖 NeonSAN 专属术语**，是通用研发设计文档专家。

## Common Mistakes

- **只写怎么做，不写为什么** — 决策没有理由，评审无法判断。
- **没有非目标** — 范围无限膨胀。
- **方案对比走过场** — 只有一个方案，没有对比。
- **风险未经分析** — 允许写“当前未识别新增风险”，同时说明检查范围、依据和未验证项；不为填满章节虚构风险。
- **凭记忆写行号** — 必须有当前版本的实读核验记录，相关条件变化时重新验证。
- **机械套模板** — 为"完整"增加一级章节，过度拆分。
- **需求与实现混淆** — §2 就进入代码细节。

## 输入、交付与证据复用

- 输入：需求、约束、已有分析与项目规范。
- 交付与完成条件：适合改动规模的设计文档：决策、适用的异常/并发/兼容分析和可判定验收。未决问题列出影响，不填造接口或阈值。
- 输入不足时先完成有依据的部分，仅询问影响结论或执行的关键缺口。
- 交接证据包含仓库、commit、文件或符号、结论与验证状态。同一版本且相关文件与运行条件未变化时复用已核验记录；版本、文件或关键条件变化时重核相关结论，不重复开展全部研究。
