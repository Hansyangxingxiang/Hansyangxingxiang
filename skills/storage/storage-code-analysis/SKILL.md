# Storage Code Analysis — 带问题沿证据链行走

## Overview

源码分析不是通读代码，而是**带问题沿证据链行走**：从入口出发，沿调用链走到关键函数，记录证据，区分"源码里写了什么"（事实）与"行为是否符合预期"（推测）。核心产出是**单功能分析卡片**，每条结论带 `file:line`。

## When to Use

- 理解某个功能如何实现（如 DISCARD 如何下发、COW 如何触发）
- 追踪 IO 路径 / 函数调用链 / 数据结构
- 需要区分"源码事实"与"推测"时
- 为排障（storage-debug）、方案（design-document）、文章（wechat-tech-article）提供源码证据

## 核心方法

### 1. 确定版本与入口
- 记录仓库、commit、相关构建选项和运行配置；未知项明确标注
- 区分直接调用、异步队列/回调和运行时分派；记录注册点、调度条件、完成通知与跨线程边界
- 从问题反推入口：系统调用、消息处理、命令处理、定时器
- 用 Grep 按函数名/字符串/日志定位，**不信任记忆中的行号**

### 2. 建立调用链
- 从入口沿调用关系逐层走，记录每一跳的 `file:line`
- 用 Grep 找函数定义与调用点，用 Read 读关键函数体
- 画调用链 ASCII 图，标注每层的输入/输出

### 3. 定位关键函数 / 数据结构
- 找到决定行为的关键函数与数据结构（结构体、枚举、标志位）
- 读结构体定义，理解字段含义与生命周期

### 4. 记录四要素
对每个关键点记录：
- **位置**：`file:line`
- **函数**：函数名 + 一句话职责
- **意图**：设计理由；注释或历史记录可作为依据，仅由命名和上下文推导的理由标为推断
- **运行路径**：什么条件下走到这里，输入输出是什么

### 5. 区分事实与推测
- **事实**：源码里明确写的——函数存在、调用关系、条件分支、默认值
- **推测**：行为是否符合预期、性能影响、边界情况——标注"推测"，需要实验验证

## 单功能分析卡片模板

```
## 功能：<功能名>

### 分析范围
- 仓库 / commit：<版本>
- 构建与运行条件：<选项、配置、平台；未知项>

### 入口
- <入口函数> @ <file:line>
- 触发条件：<什么操作/消息/调用触发>

### 调用链
<ASCII 图：入口 → ... → 关键函数>

### 关键函数
| 位置 | 函数 | 意图 | 运行路径 |
|---|---|---|---|
| file:line | name | 一句话 | 条件/输入/输出 |

### 关键数据结构
- <结构体> @ <file:line>：字段含义

### 事实 vs 推测
- 事实：<源码明确写的>
- 推测：<需要实验验证的>

### 待验证
- <下一步实验/验证项>
```

## Common Mistakes

- **凭记忆写行号** — 行号会漂移，必须有当前版本实读记录；相关文件、版本或条件变化时重新核验
- **把推测当事实** — "应该会发 DISCARD" 不是 "源码里发了 DISCARD"
- **只读函数不读调用上下文** — 行为由调用路径决定，不是单函数决定
- **跳过数据结构** — 字段含义不清，逻辑必然理解错
- **不记录位置** — 结论没有 `file:line` 就无法复核

## 输入、交付与证据复用

- 输入：问题、代码位置、版本与运行条件。
- 交付与完成条件：分析卡片：版本、调用链、证据表、推断和待验证项。以关键问题有可追溯回答或明确证据缺口为完成条件。
- 输入不足时先完成有依据的部分，仅询问影响结论或执行的关键缺口。
- 交接证据包含仓库、commit、文件或符号、结论与验证状态。同一版本且相关文件与运行条件未变化时复用已核验记录；版本、文件或关键条件变化时重核相关结论，不重复开展全部研究。
