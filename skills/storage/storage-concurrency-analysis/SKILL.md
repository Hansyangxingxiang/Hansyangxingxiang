# 存储并发与一致性分析（Storage Concurrency & Consistency Analysis）

对存储系统中的**并发操作对**、**竞态窗口**、**数据一致性**与**数据安全（数据丢失 / 数据复活）**做系统性分析。

本技能是 `storage-code-analysis`（源码分析）、`design-document`（架构与正式设计）、`storage-debug`（排障）的**并发侧互补**：把"并发 / 竞态 / 一致性 / 安全"独立成一套可复用的分析方法论，专门回答两个问题——

> **这个并发场景下，会不会丢数据？会不会数据复活？靠什么机制保证？怎么验证？**

## When to Use / NOT

出现以下任意情况时加载本技能：

- 用户要求分析存储并发 / 竞态 / 一致性 / 数据安全，或列出具体场景（如"分析 Write 和 Discard 并发""Snapshot 和 Write 并发会怎样"）。
- 用户使用关键词：并发 / 竞态 / race / 一致性 / 原子性 / 数据丢失 / 数据复活 / 数据安全 / 读后写 / 写后读 / COW / 快照一致性 / 克隆共享 / 回收竞态 / 迁移并发 / 重建并发 / 双写 / 脏读 / 幻读 / 顺序保证。
- 用户要求画并发时序图、评估某功能对一致性与安全的影响，或判断现有保护机制是否足够。
- 用户给出下方 14 场景矩阵中的任意一个。

**不适用（交给相邻技能）**：

- 只需要读懂源码、梳理调用链，没有并发问题：`storage-code-analysis`。
- 已有具体故障现象（空间未释放、IO 卡死、数据不一致现场）要反推根因：`storage-debug`。
- 要为并发保护机制产出正式设计文档、接口与测试方案：`design-document` 主导；本技能只提供并发分析结论。

> 若用户尚未给出现有代码 / 架构，先按 **§前置：建立并发模型** 引导其提供，或显式标注"现有实现待补"。本技能不脱离目标系统凭空给出"标准答案"——同一对操作在不同系统（Linux block layer / 文件系统 / 卷管理 / Ceph RBD / SPDK / 目标系统）下的保护机制差异巨大。

## 核心原则（硬性规则）

1. **事实 / 分析 / 推测三级标注**：
   - `[事实]`：来自目标系统源码（文件:行号）、协议规范、或用户确认的架构。
   - `[分析]`：基于事实的合理推断。
   - `[推测]`：无法直接验证、需实验 / 源码 / 用户确认才能定的结论。
   - 引用实现必须给真实模块 / 函数 / 文件:行号，禁止虚构 API 或函数名。
2. **先结论后细节**：每个场景先给一句话结论（尤其先回答"丢数据？复活？靠谁保护？"），再展开 11 维分析。
3. **优先级恒定：稳定性 > 性能 > 新功能**。任何并发设计取舍先论证不破坏数据正确性。
4. **两个安全终判不可跳过**：每个场景**必须**显式回答"是否可能数据丢失"与"是否可能数据复活"。这两项是存储安全的红线。
5. **并发窗口是第一性原理**：竞态不是"两个操作同时发生"，而是"两个操作的关键子步骤以某种交错发生，且没有任何机制保证该交错安全"。必须先定位窗口，再谈保护。
6. **谁负责保护必须落到层**：保护责任要么在某一层（block / fs / 卷管 / 副本层），要么跨层协调；模糊的"系统会处理"是分析失败的标志。

## 前置：建立目标系统的并发模型（所有场景的共用起点）

在套用 14 场景前，先把目标系统的并发骨架还原清楚（必要时调用 `storage-code-analysis` 落地源码）：

1. **分层与责任边界**：IO 路径上各层（应用 → 文件系统 / 卷管 → 块设备 → 传输 NVMe-oF/RDMA → 远端存储 / 副本 / EC）各自负责什么一致性？discard / snapshot / clone / COW 由哪层发起、哪层执行？
2. **地址映射模型**：LBA → 物理区段（extent）的映射表在哪、谁更新、是否原子、是否持久化？thin provisioning 下"分配"与"写入"是否分离？
3. **并发原语清单**：已有哪些锁 / 原子 / 引用计数 / 版本号（generation/epoch）/ 租约 / journal 顺序？锁的粒度（per-volume / per-extent / per-range / per-tree-node）与锁序？
4. **关键状态机**：extent 状态（FREE/ALLOCATED/WRITTEN/SHARED/RECLAIMING）、卷/快照/克隆状态、recovery/migration/rebuild 状态。
5. **崩溃一致性模型**：断电后靠什么恢复（journal/WAL、COW、元数据 checksum + scrub）？哪些操作是幂等的？

把以上 5 点列成"前置事实表"，其余 14 场景都基于它展开。

## 14 场景总览矩阵

| # | 场景 | 并发双方 | 核心风险关键词 | 数据丢失 | 数据复活 | 典型保护机制 |
|---|------|----------|----------------|----------|----------|--------------|
| 1 | Read / Write | 读 vs 写（同 LBA 区间） | 脏读 / 撕裂读 / 读偏移 | 通常否 | 否 | IO 序列化 / 原子 sector 写 / 版本 |
| 2 | Write / Write | 写 vs 写（同 LBA 区间） | 丢失更新 / 撕裂写 / 部分写 | 可能（覆盖未提交） | 否 | 区间锁 / 原子写 / journal |
| 3 | Write / Discard | 写 vs 回收（同 LBA 区间） | 写丢失 / 写落到已回收 extent | 可能 | 否 | 区间锁 / 分配-写原子 |
| 4 | Read / Discard | 读 vs 回收（同 LBA 区间） | 读到已释放区间语义未定义 | 否 | 可能（未清零泄露） | discard 语义定义 / zero-fill |
| 5 | Snapshot / Write | 建快照 vs 写 | 快照点一致性 / 写是否被纳入 | 否（除非丢失写） | 否 | 原子元数据提交 / COW 顺序 |
| 6 | Snapshot / Discard | 建快照 vs 回收 | 快照数据被回收 / 共享 extent 误释放 | 可能 | 可能 | 引用计数 / 快照 pin |
| 7 | Clone / Write | 建克隆 / 断共享 vs 写 | 克隆可见性 / COW 拷贝旧值 | 可能（拷贝错） | 可能 | COW + refcount + 区间锁 |
| 8 | Clone / Discard | 克隆回收 vs 父/子 discard | 共享 extent 双释放 / 误回收 | 可能（双释放） | 可能 | 引用计数原子 dec |
| 9 | COW / Write | COW 读旧值 vs 写 | COW 读到未提交 / 撕裂旧值 | 可能（拷贝错） | 否 | COW 在写前完成读 |
| 10 | COW / Discard | COW 读旧值 vs discard 旧值 | COW 拷贝到已释放数据 | 可能（拷贝错） | **极可能** | discard 不释放仍被引用 extent |
| 11 | Recovery / Write | 数据恢复 vs 客户端写 | 恢复覆盖新写 / 新写丢失 | 可能 | 可能（旧副本复活） | 版本号 / 租约 / 恢复前冻结 |
| 12 | Recovery / Discard | 恢复 vs 回收 | 恢复对象被误回收 | 可能 | 可能 | 恢复态 pin / 回收避让 |
| 13 | Migration / IO | 数据迁移 vs 客户端 IO | 迁移读到旧/新 / IO 落到错端 | 可能 | 可能 | 双写 / 重定向 / 版本路由 |
| 14 | Rebuild / IO | 重建冗余 vs 客户端 IO | 重建基于旧数据 / IO 读 stale | 可能 | 可能（旧条带复活） | 重建版本 / 写时更新 / 租约 |

> 上表为概览，每个场景的完整 11 维分析见 `references/scenarios.md`。

## 通用分析框架（每个场景必答的 11 问）

对任意一个并发场景（记为 **OpA ‖ OpB**），按 11 个维度逐项分析。完整引导、判定标准与套用新场景的方法见 `references/framework.md`；这里只保留维度索引：

1. 操作发生顺序（枚举危险交错） · 2. 数据生命周期 · 3. 状态变化 · 4. 并发窗口 · 5. 是否存在竞态（是/否/条件性） · 6. 谁负责保护（责任层） · 7. 锁/版本/状态机制如何关闭窗口 · 8. 崩溃/掉电/分区下的结果 · 9. 是否可能数据丢失（必答） · 10. 是否可能数据复活（必答） · 11. 如何验证（动态 + 静态 + 预期观测结果）。

## 最终合成格式

每个场景分析的交付物统一收敛为这条链路（必要时再画图）：

```
并发场景  →  执行时序（含危险交错）  →  状态变化  →  风险（丢数据?/复活?）  →  保护机制  →  验证方法
```

输出骨架：

```
# <场景名> (OpA ‖ OpB)
## 一句话结论（含：是否竞态 / 是否丢数据 / 是否复活 / 谁保护）
## 执行时序
   - 交错1（安全）
   - 交错2（危险，标注窗口）
## 状态变化（状态机 / 引用计数迁移）
## 风险
   - 数据丢失：是/否 + 条件
   - 数据复活：是/否 + 条件
## 保护机制（锁/版本/状态 + 如何关闭窗口）
## 验证方法（动态 + 静态 + 预期结果）
## 图示（默认 ASCII；目标平台支持 Mermaid 时可用 references/mermaid-templates.md）
## 未验证事项（[推测] 级清单）
```

## 图示表达

- Claude Code 终端默认使用 ASCII：用编号步骤、`|` / `+--+` 和箭头表达交错；在危险交错处直接标注"并发窗口"。
- 目标平台支持 Mermaid 时，可用 `sequenceDiagram` 表达交错（`Note over` 标注并发窗口与危险点），用 `stateDiagram-v2` 表达 extent / 卷 / 恢复状态机；可复用片段见 `references/mermaid-templates.md`。
- 不要为画而画——只在交错能说明问题时才画。图示中的模块、锁和状态必须在正文有对应解释。

## 与其他 Skill 协作

- `storage-code-analysis`：提供 `file:line` 级源码事实、调用链、锁与状态机位置。本技能只做并发推理，不重复读源码；缺少源码时标注"现有实现待补"。
- `storage-debug`：提供故障现象、日志、复现条件和修复证据。本技能据此定位竞态窗口；不要把单条日志直接升级为竞态或根因。
- `design-document`：承接并发保护方案、接口契约、兼容升级与测试设计。本技能输出场景结论、危险交错与未验证项，作为设计输入，不代替正式设计文档。

## 输入、交付与证据复用

**输入**：目标系统与版本；分层与责任边界；锁 / 原子 / 版本 / 租约清单；extent、卷、快照、克隆、迁移状态机；IO 路径与关键 `file:line`。缺失项标为"待补"，不得用通用经验替代。

**交付与完成条件**：每个场景至少给出——

- 是否存在竞态：是 / 否 / 条件性；
- 危险交错与并发窗口；
- 是否可能数据丢失、是否可能数据复活，以及触发条件；
- 保护责任层与实际机制；
- 验证方法与预期观测结果；
- 未验证事项及补齐方式。

允许结论为"未定位 / 条件性竞态 / 需实验确认"；不得为了完整性编造锁、字段或实验结果。

**证据复用**：通用规则见 `references/shared-method.md`；本技能按场景粒度只重核受版本 / 配置 / 代码变化影响的部分，并说明哪些结论复用、哪些重核。
