## 1. Read / Write（读 vs 写，同 LBA 区间）

**一句话结论**：`[分析]` 若写以 sector/原子块粒度提交且读不跨越未提交边界，则无数据丢失、无复活；风险点是**撕裂读（torn read）**与**读偏移（read skews to pre/post value）**。保护靠 IO 序列化或原子写粒度。

1. **操作发生顺序**
   - 交错1（安全）：W 完成 ack 后 R 发起 → R 读到新值。
   - 交错2（安全）：R 完成后 W 才发起 → R 读到旧值。
   - 交错3（危险）：R 跨越 W 的"部分提交"——R 的前半读旧值、后半读新值（跨原子粒度时）。
2. **数据生命周期**：数据在 buffer/journal/磁盘间迁移；R 观察到的版本取决于其发起时刻相对 W 提交点的先后。
3. **状态变化**：extent 状态 `WRITTEN`（旧）→ `WRITTEN`（新）；映射表不变（同 LBA）。无 refcnt 变化。
4. **并发窗口**：`[W 开始写, W ack]` 与 `[R 发起, R 完成]` 重叠，且 R 的读取粒度 > W 的原子提交粒度。
5. **是否存在竞态**：条件性。**撕裂读 / 读偏移**（非"同时发生"的模糊竞态，而是非原子可见性）。
6. **谁负责保护**：block layer / 卷管层保证"单次读要么全旧要么全新"；应用层负责更高语义（如读一致性视图）。
7. **锁/版本/状态机制**：写以 sector（512B）或原子块（常 4K，依赖设备 `atomic_write` 能力）粒度完成；读同粒度对齐则天然无撕裂。粗粒度可用 `L(range)` 串行化 R 与 W，或用 version（读时取 generation，避免半新半旧）。
8. **异常下的结果**：窗口内崩溃 → 恢复后该 LBA 要么旧要么新（取决于 journal 是否重放该写），不会"半块"。`[分析]`
9. **是否可能数据丢失**：否（用户视角）。写 ack 后不会因并发读而丢失。
10. **是否可能数据复活**：否。
11. **如何验证**：fio `rw=randrw` 开 `verify=...` 校验，长时间跑看是否有校验错（撕裂会暴露）；用 `bpftrace` 在 W 的提交前后注入延迟放大窗口，观察读校验。静态：审查 W 的提交粒度是否 ≥ R 的读取粒度。

## 2. Write / Write（写 vs 写，同 LBA 区间）

**一句话结论**：`[分析]` 危险点是**丢失更新**与**撕裂写**。若两写各自按 atomic 块提交且后 ack 者覆盖先 ack 者，则"最后写赢"是预期语义（非丢失）；真正丢失发生在"两写共享缓冲/映射更新非原子"时。保护靠区间锁或原子映射更新。

1. **操作发生顺序**
   - 交错1：W_a 完成 → W_b 完成 → 终值 = b（预期 last-write-wins）。
   - 交错2（危险）：W_a 与 W_b 都读到同一旧映射、各自分配/写，后者提交覆盖前者未持久部分 → **丢失更新**（a 的部分丢失）。
   - 交错3（危险）：W 以非原子粒度提交，另一 W 读到半新半旧 → **撕裂写**。
2. **数据生命周期**：两股数据竞争同一 LBA 的"committed"位置。
3. **状态变化**：映射表 `LBA→phys_a` 与 `LBA→phys_b` 竞争；若分配与映射更新非原子，`rc` 可能出现悬空。
4. **并发窗口**：`[分配/映射更新, 数据 commit]` 重叠且**无互斥**。
5. **是否存在竞态**：是（条件性）。**丢失更新 / 撕裂写**。
6. **谁负责保护**：卷管/FS 层对冲突 LBA 区间加 `L(range)`；或映射更新用 atomic/seqlock。
7. **锁/版本/状态机制**：`L(range)` 覆盖整个 alloc→write→commit；或 COW/ROW 流派使两写各自落到不同物理 extent、最后原子切换映射（last-writer 通过 generation 仲裁）。
8. **异常下的结果**：窗口崩溃 → 可能两 extent 都分配但仅一个被映射引用 → 另一个成孤儿（空间泄漏，非数据丢失）；或映射指向未写完 extent → 读到半新。`[分析]`
9. **是否可能数据丢失**：可能（当丢失更新发生时，a 的写入不可见）。但 last-write-wins 语义下不算丢失。
10. **是否可能数据复活**：否（同 LBA 竞争，不产生"已删数据复活"）。
11. **如何验证**：并发两写同范围 + 校验模式（如每写填唯一 pattern），读回比对；注入延迟放大窗口；崩溃后 scrub 检查孤儿 extent。静态：审查映射更新是否原子、是否有区间锁。

## 3. Write / Discard（写 vs 回收，同 LBA 区间）

**一句话结论**：`[分析]` **最经典的危险场景之一**。若 discard 在 write 的"映射已更新但数据未落盘"之间释放物理 extent，写会落到已回收空间 → **写丢失**；或 write 后 discard 释放了刚写入的 extent → ack 后数据消失。保护靠 `L(range)` 覆盖 alloc→write→commit 全区间，使 discard 必须等写完成。

1. **操作发生顺序**
   - 交错1（安全）：W 完成 ack → D 释放（释放的是"新写入后"的区间，符合用户意图）。
   - 交错2（危险）：`W2 更新映射(LBA→phys_p)` → `D1 标记空闲` → `D2 释放 phys_p` → `W3 写 phys_p`（phys_p 已被回收/可能被复用）→ **写丢失/写到他人空间**。
   - 交错3（危险）：`W ack` → `D 释放刚写入 extent`（若 D 基于过期映射认为该区间空闲）→ **ack 后数据消失**。
2. **数据生命周期**：W 把 extent 推到 `WRITTEN`；D 把它拉回 `FREE`/`RECLAIMING`。重叠时生命周期对冲。
3. **状态变化**：`rc(extent)`：W 使 extent 被本卷引用；D 尝试 dec。若 D 在 W 完成前 dec，且 `rc` 误到 0 → 回收。
4. **并发窗口**：`[W2 映射更新, W3 数据 commit]`（alloc 早于数据）与 `[D1, D2]` 重叠。
5. **是否存在竞态**：是。**TOCTOU（检查空闲 vs 实际刚被分配写入）/ use-after-free / 写丢失**。
6. **谁负责保护**：卷管/FS 层必须对 `[alloc, commit]` 区间持 `L(range)`，discard 同区间须等待。
7. **锁/版本/状态机制**：`L(range)` 串行化 W 与 D；或 discard 仅释放"映射中已被新版本完全覆盖"的旧 extent，且以 generation 判定。
8. **异常下的结果**：窗口崩溃 → 映射指向已回收 extent → 读返回零/旧/他人数据；或 extent 双归属。`[分析]`
9. **是否可能数据丢失**：**可能**（交错2/3）。
10. **是否可能数据复活**：否（本场景是写被吞，非旧数据重现；复活见场景 4/10）。
11. **如何验证**：fio `trimwrite` 或 `randwrite`+`trim` 并发 + `verify`；在 `W2` 与 `W3` 间注入延迟，强制 D 插入；崩溃后 scrub 检查"已 ack 写入是否可读回"。静态：审查 discard 路径是否对目标区间持锁、是否基于最新映射。

## 4. Read / Discard（读 vs 回收，同 LBA 区间）

**一句话结论**：`[分析]` 读本身不会让数据"复活"，但 discard 的**语义定义**决定读返回值：若 discard 仅"建议"且未清零，读可能返回旧数据 → **数据复活/跨租户泄露**；若 discard 是"命令"且 zero-fill，读到零（安全）。风险在**未清零复用**。

1. **操作发生顺序**
   - 交错1（安全语义）：D 完成后 R 读 → 返回零（命令式 discard + zero-fill）或 undefined-but-zeroed。
   - 交错2（危险）：D 释放 extent 但**未清零** → 该 extent 被重新分配给新 LBA/新租户 → 新读者读到**旧数据** → **复活/泄露**。
   - 交错3：R 正在进行（已映射旧 phys）→ D 释放该 phys 并复用 → R 后半读到新数据（撕裂/幻读）。
2. **数据生命周期**：extent `WRITTEN → (D) RECLAIMING → 复用(FREE→ALLOCATED)`；清零步骤有无决定复活。
3. **状态变化**：`rc(extent)` 到 0 触发回收；是否 zero-fill 是策略。
4. **并发窗口**：`[D 释放, 新分配者写入/读取]` 之间若缺清零，即复活窗口。对"进行中的 R"窗口为 `[R 映射旧 phys, R 完成]` 与 `[D 释放该 phys]` 重叠。
5. **是否存在竞态**：条件性。**幻读 / 跨租户数据泄露**（取决于 discard 是否保证清零）。
6. **谁负责保护**：block/设备层保证 discard 语义（NVMe DSM 不保证清零）；卷管/FS 层负责 `secure discard`/zero-fill 或分配前清零。
7. **锁/版本/状态机制**：分配器保证"新分配 extent 先清零再交付"；或用 `secure erase`；或 COW 系统根本不立即复用。
8. **异常下的结果**：崩溃在"释放未清零"态 → 重启后该 extent 仍含旧数据，被复用即泄露。`[分析]`
9. **是否可能数据丢失**：否（用户视角，读不破坏数据）。
10. **是否可能数据复活**：**可能**（当 discard 不保证清零且 extent 被复用）。这是合规硬伤（删除权/租户隔离）。
11. **如何验证**：分配旧数据所在 extent 给新卷/新文件，读取检查是否含旧内容（模式校验）；`fio` 写 pattern→discard→重分配→读校验。静态：审查分配器是否在交付前清零，是否区分 `discard` vs `secure discard`。

## 5. Snapshot / Write（建快照 vs 写，同卷）

**一句话结论**：`[分析]` 核心风险是**快照点一致性**：快照应捕获"某一瞬间之前的所有已提交写"，之后的写不应出现在快照里（或按 COW 流派，写触发拷贝旧值进快照）。是否丢数据取决于"快照瞬间是否有写被吞/重复计入"。保护靠**快照提交原子性 + 写冻结/COW 顺序**。

1. **操作发生顺序**
   - COW 流派：SNAP 提交瞬间，后续 W 触发"先拷贝旧值到快照专属 extent，再写新值"。W 在 SNAP 前 → 旧值已在数据区，快照共享；W 在 SNAP 后 → COW 拷贝旧值，快照保留旧。
   - ROW 流派：SNAP 后 W 重定向到新 extent，元数据版本切换；快照指向旧版本链。
   - 危险交错：SNAP 提交与某 W 的"映射更新"交错 → 该写被计入或遗漏不一致（取决于提交顺序）。
2. **数据生命周期**：数据在"当前活动链"与"快照冻结链"间分流；COW 使旧值被快照"接管"。
3. **状态变化**：卷状态 `ACTIVE → FROZEN(瞬时) → ACTIVE`；新快照对象 `CREATING → ACTIVE`；被快照引用的 extent `rc++`。
4. **并发窗口**：SNAP 元数据提交的临界区 vs W 的映射更新临界区。
5. **是否存在竞态**：条件性。**元数据提交非原子导致快照点"半旧半新"**（非用户视角的写丢失，是快照不一致）。
6. **谁负责保护**：卷管层：快照元数据提交用原子事务（journal 单条记录），或提交前短暂 freeze 写（加卷级/树级锁）。
7. **锁/版本/状态机制**：快照提交 = 原子切换"当前版本指针"；COW 在切换前完成旧值拷贝；或 freeze 写直到快照元数据持久化。generation 递增。
8. **异常下的结果**：SNAP 提交中途崩溃 → 要么快照不存在（回滚），要么完整（journal 重放决定）；写要么在快照内要么外，不会"半计入"。`[分析]`
9. **是否可能数据丢失**：否（除非快照提交 bug 导致某写既不在活动卷也不在快照——属实现缺陷，需 `[事实]` 核实）。
10. **是否可能数据复活**：否（快照捕获的是合法旧值，非"已删数据"）。
11. **如何验证**：建快照瞬间并发随机写已知 pattern，快照完成后比对快照内容 + 活动卷内容，确认"任一写要么在快照要么在活动卷，不重复不遗漏"；崩溃注入在 SNAP 提交临界区，重启后校验快照完整性。静态：审查快照元数据提交是否为单原子事务。

## 6. Snapshot / Discard（建快照 vs 回收，同 LBA 区间）

**一句话结论**：`[分析]` 危险点是 **discard 误释放仍被快照共享的 extent** → 快照后续读返回零/旧值（快照数据损坏），以及**已 discard 区间被快照"复活"为可读旧值**（若 discard 未真正回收物理）。保护靠 `rc(extent)`：仅当 `rc` 降为 0 才回收；快照持有引用则 pin 住。

1. **操作发生顺序**
   - 安全：D 仅 release 本卷对该 extent 的引用（`rc--`）；若 `rc>0`（快照仍引用）→ 物理不回收，快照安全。
   - 危险：D 直接释放物理 extent（忽略 `rc` 或 `rc` 计算错误）→ 快照读该 extent → 返回零/他人数据 → **快照数据丢失/复活旧值**。
   - 危险2：D 标记区间空闲后未清零即复用，快照基于旧映射仍指向该 phys → 快照读到新写入者数据（**复活**：快照看到不该看到的未来数据）。
2. **数据生命周期**：extent 被卷与快照共享（`rc>=2`）；D 试图降到 `rc==0` 才回收。
3. **状态变化**：`rc(extent)`：`卷1 + 快照N`；D 使卷侧 `rc--`；仅 `==0` 触发 `RECLAIMING`。
4. **并发窗口**：SNAP 提交（递增 `rc`/`pin`）与 D 的 `rc--`/释放 之间，若 `rc` 操作非原子。
5. **是否存在竞态**：条件性。**double-free 类 / 共享 extent 误释放**（当 `rc` 非原子或 discard 绕过 `rc`）。
6. **谁负责保护**：卷管层引用计数；discard 路径**必须**走 `rc--` 且判断 `==0`，不得直接物理释放。
7. **锁/版本/状态机制**：`atomic rc`；discard 释放 = `if (dec_and_test(rc)==0) reclaim()`；快照创建 = `rc++` 并持久化；映射表用 seqlock 防半更新。
8. **异常下的结果**：窗口崩溃 → `rc` 可能为 1 但物理已被释放（悬空引用）→ 快照读坏；或 `rc` 负值（double-free）。`[分析]`
9. **是否可能数据丢失**：**可能**（快照引用的 extent 被误回收 → 快照数据不可恢复）。
10. **是否可能数据复活**：**可能**（discard 后快照仍指向旧 phys，读到被复用后的新数据）。
11. **如何验证**：建快照后对该卷 discard 共享区间，校验快照内容不被破坏；并发 discard + 建快照，检查 `rc` 不变式（`rc>=引用者数`，无负值）；崩溃注入，重启 scrub 查悬空引用。静态：审查 discard 是否走 `rc--` 而非直接释放。

## 7. Clone / Write（建克隆 / 断共享 vs 写，克隆卷）

**一句话结论**：`[分析]` 克隆初建时与父卷**共享** extent（COW/clone-on-write）。危险在 **clone 的 COW 拷贝了错误的旧值**（并发写已改父卷），或**写穿透到共享 extent 破坏父卷**。保护靠 `rc` + 区间锁确保"COW 先完成旧值拷贝，再允许新写覆盖"。

1. **操作发生顺序**
   - 安全：CLONE 创建（共享 `rc++`）→ 对克隆的 W 触发 COW：拷贝父旧值到克隆专属 extent → 写新值。父卷不受影响。
   - 危险：CLONE 创建与对**父卷**的 W 并发 → 克隆的 COW 拷贝时，父卷该 extent 正被改写 → **拷贝到撕裂/未提交值**（拷贝错/silent corruption）。
   - 危险2：W 直接写到共享 extent（未先 COW 断共享）→ 父卷与克隆互相污染。
2. **数据生命周期**：extent 从"父独占"→"父子共享(`rc=2`)"→ COW 后"各自独立"。
3. **状态变化**：CLONE 使 `rc(extent)++`；W 触发 COW：`rc` 行为（父 `rc--` 共享解除，克隆获独立 extent）。
4. **并发窗口**：CLONE 的 COW"读旧值"子步骤 与 父卷 W 的"写新值"子步骤 重叠。
5. **是否存在竞态**：是（条件性）。**COW 读未提交 / 共享 extent 双写污染**。
6. **谁负责保护**：卷管层：COW 须对目标区间持 `L(range)`，且"读旧值→写新 extent→切换映射"为原子临界区；父卷写同区间须等待。
7. **锁/版本/状态机制**：`L(range)` 覆盖 COW 全程；或用快照式 generation（COW 基于固定 generation 的旧值，不受后续写影响）。
8. **异常下的结果**：窗口崩溃 → COW 半完成：克隆 extent 部分旧部分新，或映射指向未完成 extent。`[分析]`
9. **是否可能数据丢失**：**可能**（拷贝错，克隆内容 silent corruption；比直接丢失更危险）。
10. **是否可能数据复活**：可能（若 COW 拷贝到已被父卷覆盖的旧值语义错误，克隆"复活"了不该有的视图——视语义定义）。
11. **如何验证**：建克隆瞬间并发写父卷已知 pattern，校验克隆内容（应等于 COW 时刻的父卷快照值，不撕裂）；注入延迟在"COW 读旧值"与"父写"之间；崩溃后 scrub 克隆完整性。静态：审查 COW 是否对区间加锁、是否基于固定版本读旧值。

## 8. Clone / Discard（克隆回收 vs 父/子 discard，共享 extent）

**一句话结论**：`[分析]` 经典 **double-free / 共享 extent 双释放** 场景。克隆与父卷共享 extent（`rc=2`），任一方 discard 仅应 `rc--`；若某方 discard 直接物理释放（或 `rc` 非原子），会导致 extent 被释放两次或负计数 → 父/子数据损坏或空间复用冲突。保护靠 `atomic rc` + discard 仅 `rc==0` 回收。

1. **操作发生顺序**
   - 安全：父 discard → `rc--`（仍 ≥1，克隆持有）→ 不回收；克隆 discard → `rc--` → `==0` → 回收。对称。
   - 危险：两方并发 discard 各自 `rc--` 但读取 `rc` 都看到 2 → 都判断"我释放后还有别人"或都判断"到我这归零" → 双释放 / `rc` 变负 / 回收两次。
   - 危险2：某方 discard 绕过 `rc` 直接释放物理 → 另一方读该 extent 坏。
2. **数据生命周期**：extent `共享(rc=2) → 单方释放(rc=1) → 双释放(rc=0 或负)`。
3. **状态变化**：`rc(extent)` 的 `dec` 操作并发。
4. **并发窗口**：父 discard 的 `rc--` 与 克隆 discard 的 `rc--` 之间（非原子 read-modify-write）。
5. **是否存在竞态**：是。**double-free / 引用计数竞态（lost update on rc）**。
6. **谁负责保护**：卷管层引用计数；discard 释放必须 `atomic dec_and_test`。
7. **锁/版本/状态机制**：`atomic rc` 的 `dec_and_test(rc)==0` 才 reclaim；映射/共享树用锁保护结构更新。
8. **异常下的结果**：窗口崩溃 → `rc` 不一致（负/悬空）→ 该 extent 被复用且仍被引用 → 数据损坏。`[分析]`
9. **是否可能数据丢失**：**可能**（双释放导致一方仍引用已被回收/复用的 extent）。
10. **是否可能数据复活**：**可能**（回收后 extent 被复用，原引用者读到新数据）。
11. **如何验证**：父+克隆并发 discard 同一共享区间，重复大量次，检查 `rc` 不变式（无负值、回收次数==真正无引用次数）；崩溃注入后 scrub 查悬空/双释放。静态：审查 discard 的 `rc` 操作是否为原子 `dec_and_test`。

## 9. COW / Write（COW 读旧值 vs 写，同 LBA）

**一句话结论**：`[分析]` COW 机制本身要先"读旧值写新 extent"再更新映射。危险在 **COW 读到的旧值正被并发 W 改写** → 拷贝到撕裂/未提交值（silent corruption），或 **COW 与 W 都落到同一新 extent 冲突**。保护靠 COW 全程持 `L(range)`，使并发 W 等待。

1. **操作发生顺序**
   - 安全：COW 触发 → 锁区间 → 读旧值 → 写新 extent → 切换映射（本卷指向新 extent，旧 extent 归快照/原者）→ 解锁；期间 W 阻塞。
   - 危险：COW 的"读旧值"与 W 的"写新值"无互斥 → COW 读到半新半旧 → **拷贝错**。
   - 危险2：COW 与 W 都基于同一旧映射分配新 extent，提交时后者覆盖前者 → 丢失更新。
2. **数据生命周期**：旧extent 被"接管"（快照/原卷），新 extent 承载新值。
3. **状态变化**：映射 `LBA→old` 切换为 `LBA→new`；`rc(old)` 转移。
4. **并发窗口**：COW 的"读旧值"子步骤 与 W 的"写旧 extent"子步骤 重叠（无锁时）。
5. **是否存在竞态**：是（条件性）。**COW 读未提交 / 撕裂旧值拷贝**。
6. **谁负责保护**：卷管层：COW 临界区持 `L(range)`，覆盖"读旧→写新→切映射"。
7. **锁/版本/状态机制**：`L(range)` 使 COW 与 W 互斥；或 COW 基于固定 generation 读旧值（旧值版本固定，不受 W 影响）。
8. **异常下的结果**：窗口崩溃 → COW 半完成，新 extent 部分旧部分新，映射可能指向未写完 extent。`[分析]`
9. **是否可能数据丢失**：**可能**（拷贝错 = 新写入内容 silent corruption，用户以为写成功但内容错）。
10. **是否可能数据复活**：否（本场景是拷贝错，非旧数据重现；复活见 10）。
11. **如何验证**：触发 COW（如首次写快照后卷）同时并发写同 LBA 已知 pattern，校验 COW 结果无撕裂；注入延迟在"读旧值"与"写"之间；崩溃后 scrub。静态：审查 COW 是否持区间锁或基于固定版本。

## 10. COW / Discard（COW 读旧值 vs discard 旧值，同 extent）—— 复活高发区

**一句话结论**：`[分析]` **数据复活的最高危场景之一**。COW 需要先读"旧值"拷贝到新 extent；若 discard 在 COW 读之前已把该 extent 释放（甚至清零/复用），COW 会拷贝到**零/他人数据/已消失的旧值** → 快照/克隆内容被固化为不确定的脏数据（即"已删除/已释放的数据以错误形式复活"）。保护靠 **discard 不释放仍被引用（含即将 COW）的 extent**，即 `rc` 与 COW 的引用必须同步。

1. **操作发生顺序**
   - 安全：D 仅 `rc--`，因 COW 已持有引用（`rc>=1`）→ 物理不释放 → COW 读到正确旧值。
   - 危险：D 释放物理 extent（绕过 `rc` 或 `rc` 误判）→ COW 读该 extent → 读到零/被复用数据 → **拷贝脏值进快照/克隆**（复活 = 快照固化了不该有的内容）。
   - 危险2：D 释放后该 extent 被新数据写入，COW 读到的"旧值"实为**未来数据** → 快照看到不该看到的（复活的另一形态）。
2. **数据生命周期**：extent `WRITTEN → (D) RECLAIMING → 复用`；COW 试图在 `RECLAIMING` 后仍读它。
3. **状态变化**：`rc` 与 COW 的"引用意图"必须一致；若 D 的 `rc--` 与 COW 的"读"无同步 → 不一致。
4. **并发窗口**：COW 的"读旧值"子步骤 与 D 的"释放物理"子步骤 重叠，且 `rc` 未体现 COW 的引用。
5. **是否存在竞态**：是。**use-after-free（COW 读已释放 extent）/ 数据复活**。
6. **谁负责保护**：卷管层：COW 触发即视为对该 extent 持有"读引用"（纳入 `rc` 或 COW 专用引用集）；discard 须见该引用才不释放。
7. **锁/版本/状态机制**：COW 持 `L(range)` 或显式 `pin(extent)` 阻止 discard 释放；discard 释放 = `rc==0 且无 COW 引用`；或基于 generation 固定旧值版本，discard 不影响已 pin 的版本。
8. **异常下的结果**：窗口崩溃 → COW 拷贝了零/他人数据并提交到快照 → 快照内容永久错误（难发现，因无校验基准）。`[分析]`
9. **是否可能数据丢失**：**可能**（拷贝错，快照/克隆内容 silent corruption）。
10. **是否可能数据复活**：**极可能**（本场景是复活的典型路径：已释放/已覆盖数据以错误形式固化进快照/克隆，或快照读到被复用的未来数据）。
11. **如何验证**：构造"对某区间 discard 同时触发其 COW（如该区间被快照共享且正被改写）"，校验 COW 产物是否等于 discard 前的合法旧值（非零/非他人数据）；并发大量 discard+COW，scrub 快照内容；崩溃注入在"COW 读"与"D 释放"之间。静态：审查 COW 是否 pin 住 extent、discard 是否检查 COW 引用。

## 11. Recovery / Write（数据恢复 vs 客户端写，同数据对象）

**一句话结论**：`[分析]` 恢复（从副本/EC/备份重建某对象）与客户端新写并发时，若恢复以**旧版本**覆盖新写，或新写被恢复"吞掉"，则**新写丢失**；反之若恢复用的旧副本被错误地"复活"成当前数据，则是**旧数据复活**。保护靠 **version/generation 仲裁 + 恢复前冻结/租约**。

1. **操作发生顺序**
   - 安全：REC 先读各副本 version，取 max(version) 作为权威；若客户端新写 version 更高 → REC 以新写为准，不覆盖。
   - 危险：REC 基于**过期 view**（如从旧副本/旧元数据拉取）得到低 version 数据 → 覆盖客户端已 ack 的高 version 新写 → **新写丢失**。
   - 危险2：REC 把旧副本数据写回（因误判其为最新）→ 客户端读到"已修改过的旧值" → **旧数据复活**。
2. **数据生命周期**：对象在"副本间"收敛；REC 试图把某版本提升为权威。
3. **状态变化**：对象 `version`；REC 状态 `SCANNING→COPYING→VERIFYING→DONE`；客户端写 `version++`。
4. **并发窗口**：REC 的"确定权威版本"子步骤 与 客户端 W 的"提交新 version"子步骤 重叠，且 REC 的 version 视图过期。
5. **是否存在竞态**：是（条件性）。**stale overwrite（旧覆盖新）/ 旧副本复活**。
6. **谁负责保护**：副本/EC 层：恢复以 **max(version/generation/lease)** 仲裁；恢复期间对目标对象加写租约或短暂冻结客户端写（或冲突检测后重试）。
7. **锁/版本/状态机制**：`version`/`generation` 单调；REC 提交前重新校验 version（compare-and-swap）；租约防止恢复期间客户端写逃出；冲突则 REC 放弃并重试。
8. **异常下的结果**：窗口崩溃 → 可能 REC 半写覆盖新写 → 新写丢失；或 version 回退。`[分析]`
9. **是否可能数据丢失**：**可能**（REC 旧覆盖新）。
10. **是否可能数据复活**：**可能**（REC 用旧副本覆盖，旧数据"复活"为当前值）。
11. **如何验证**：恢复进行中并发客户端写已知新 pattern，校验最终数据 == 新写（不被旧覆盖）；人为让 REC 从过期副本拉取，验证 version 仲裁是否拦截；崩溃注入在 REC 提交前。静态：审查 REC 是否以 max(version) 仲裁、提交前是否 re-check version。

## 12. Recovery / Discard（恢复 vs 回收，同 extent/对象）

**一句话结论**：`[分析]` 恢复对象正被重建时，若 discard 将其释放/复用，会导致**恢复产物丢失**或**恢复读到已释放/被复用数据**（旧数据复活）。保护靠 **恢复态 pin（recovery 持有引用，discard 避让）**。

1. **操作发生顺序**
   - 安全：REC 对目标 extent 持引用（pin）；D 见 `rc>0`/`recovery 引用` → 不释放，避让。
   - 危险：D 释放 REC 正在重建的 extent → REC 写入已回收空间（写丢失/写他人）或读到零/复用数据 → **恢复产物错 / 旧数据复活**。
   - 危险2：REC 从"源"读数据，源 extent 被 D 释放复用 → REC 拷贝到未来/他人数据。
2. **数据生命周期**：extent `重建中 → (D) 释放 → 复用`，与 REC 对冲。
3. **状态变化**：`rc` / recovery 引用集；D 的 `rc--`。
4. **并发窗口**：REC 的"读源/写目标"子步骤 与 D 的"释放"子步骤 重叠，缺 pin。
5. **是否存在竞态**：是。**use-after-free（恢复读/写已释放 extent）/ 双释放**。
6. **谁负责保护**：副本/卷管层：REC 持目标+源 extent 引用，discard 须见引用才释放。
7. **锁/版本/状态机制**：REC 持 `pin(extent)` 或 `L(range)`；discard 释放条件含"无 recovery 引用"；generation 防源数据被复用后仍被读。
8. **异常下的结果**：窗口崩溃 → REC 半完成且 extent 已释放 → 恢复对象损坏/悬空。`[分析]`
9. **是否可能数据丢失**：**可能**（恢复产物写入已回收空间）。
10. **是否可能数据复活**：**可能**（REC 读到被复用 extent 的未来/他人数据）。
11. **如何验证**：恢复进行中并发 discard 目标/源区间，校验恢复结果正确、无悬空引用；崩溃注入在 REC 读源与 D 释放之间；scrub 检查 recovery 对象的 extent 归属。静态：审查 REC 是否 pin extent、discard 是否避让 recovery 引用。

## 13. Migration / IO（数据迁移 vs 客户端 IO，同数据对象）

**一句话结论**：`[分析]` 迁移（数据在节点/设备/介质间搬动）与客户端 IO 并发时，若路由/重定向不一致，客户端 IO 可能**落到旧端（读到迁移前数据）或新端（覆盖未迁移完的数据）**，导致**丢失更新 / 旧数据复活 / 撕裂**。保护靠 **双写 / 重定向 + 版本路由 / 迁移期 IO 串行化**。

1. **操作发生顺序**
   - 双写法（安全）：迁移期间客户端 W 同时写旧端+新端，读从新端；迁移完成后切路由。
   - 重定向法：迁移期间 IO 重定向到"当前权威端"，旧端只读/停写。
   - 危险：W 落到旧端（未同步到新端），随后路由切到新端 → 该写**丢失**；或 R 落到旧端读到**迁移前旧值**（旧数据复活）；或写一半切路由 → **撕裂**。
2. **数据生命周期**：数据 `源端 → 传输中 → 目标端`，期间客户端 IO 与之交错。
3. **状态变化**：对象 `迁移状态`（源/同步中/目标）；路由表 `指向源/指向目标`；version。
4. **并发窗口**："客户端 IO 提交" 与 "迁移切换路由/完成拷贝" 之间，路由不一致。
5. **是否存在竞态**：是（条件性）。**stale write（写旧端丢失）/ 旧数据复活（读旧端）/ 撕裂**。
6. **谁负责保护**：迁移协调层（控制面）：维护路由原子切换；数据面保证迁移期 IO 不丢（双写或重定向）。
7. **锁/版本/状态机制**：路由表原子切换（单条元数据提交）；双写保证两远端一致；或"写时重定向到目标端 + 读未满部分回源"；version 保证最终以最新为准。
8. **异常下的结果**：窗口崩溃 → 路由与数据不一致：部分数据在源、部分在目标，或孤儿拷贝。`[分析]`
9. **是否可能数据丢失**：**可能**（写旧端未被同步即切换）。
10. **是否可能数据复活**：**可能**（读旧端得到迁移前旧值）。
11. **如何验证**：迁移进行中并发随机 IO 已知 pattern，迁移完成后全量校验每对象 == 最新写入；注入延迟在"路由切换"前后；崩溃注入在拷贝中途，重启校验一致性。静态：审查迁移路由切换是否原子、迁移期 IO 是否双写/重定向。

## 14. Rebuild / IO（重建冗余 vs 客户端 IO，同条带/对象）

**一句话结论**：`[分析]` 重建（RAID/EC 重建、Ceph backfill/recovery）与客户端 IO 并发时，若重建基于**过期条带/块**或客户端写未反映到重建源，会导致**重建出旧数据（旧条带复活）**或**客户端新写被重建覆盖**。保护靠 **重建以最新版本为准 + 写时更新重建源 / 冲突重试 + 租约**。

1. **操作发生顺序**
   - 安全：REBLD 读"最新"源数据（含客户端刚写的新值，因写已落源或 REBLD 见新 version）→ 重建目标；客户端 W 与 REBLD 互不覆盖（version 仲裁）。
   - 危险：REBLD 读源时客户端 W 尚未反映到该源（缓存/延迟）→ REBLD 用旧条带重建 → **旧条带复活**（冗余里是过期数据，读可能命中）。
   - 危险2：REBLD 写回重建目标时与客户端 W 冲突，REBLD 旧覆盖新 → **新写丢失**。
2. **数据生命周期**：条带 `缺失/降级 → 重建中 → 恢复冗余`；期间客户端 IO 改变源数据。
3. **状态变化**：降级状态 `DEGRADED → REBUILDING → HEALTHY`；条带 version；客户端写 `version++`。
4. **并发窗口**：REBLD 的"读源算校验/拷贝"子步骤 与 客户端 W 的"改源"子步骤 重叠，且 REBLD 源视图过期。
5. **是否存在竞态**：是（条件性）。**旧条带复活 / stale overwrite**。
6. **谁负责保护**：RAID/EC/副本层：重建以最新 version 为准；写时同步更新重建涉及的源；冲突则重建该条带重试。
7. **锁/版本/状态机制**：`version`/`generation` 仲裁；重建读源前取最新视图（compare version）；写时若条带正在重建则等待或标记"重建无效需重算"；租约防冲突。
8. **异常下的结果**：窗口崩溃 → 重建出过期条带，冗余层含旧数据，读命中即复活。`[分析]`
9. **是否可能数据丢失**：**可能**（REBLD 旧覆盖新写）。
10. **是否可能数据复活**：**可能**（重建基于过期条带 → 旧数据进入冗余层被读回）。
11. **如何验证**：重建进行中并发客户端写已知 pattern，校验重建完成后各副本/条带 == 最新写（无过期）；人为让 REBLD 源视图过期，验证 version 拦截；崩溃注入在 REBLD 读源与 W 之间；scrub 检查冗余层一致性。静态：审查 REBLD 是否以最新 version 读源、写时是否使重建无效/重试。
